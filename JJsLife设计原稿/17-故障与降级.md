# 17 · 故障与降级

> 上游：[01-不变式](01-不变式.md)（I1 / I2）｜ [05-内核接口形状](05-内核接口形状.md)｜ [11-整理会话](11-整理会话.md)

## 一、判据凭什么成立

第一判据是：**关掉所有渠道后，它是否还存在、是否还在变化。** 其前提是一个架构选择：**渠道与推理后端解耦。**

| 断了什么 | 数据 | 思考 | 整理（变化） |
|---|---|---|---|
| 渠道 | ✅ 在 | ✅ 在 | ✅ 照常 |
| DSH / 模型 | ✅ 在 | ❌ 无 | ❌ 停 |
| 内核自己 | ⚠️ 靠持久化 | — | — |

- **「还在」** 由内核的存储所有权保证（I1）。
- **「还在变化」** 由整理会话保证（11），而整理需要 DSH。

**结论：只要 DSH 活着、渠道断了，角色依然在成长。** 反过来说，若把数据交给 DSH 的 session 管，渠道一断、会话一过期，角色就真的没了。

## 二、故障分类与降级

| # | 故障 | 影响 | 降级行为 |
|---|---|---|---|
| F1 | 渠道断线 | 收不到 / 发不出 | 角色继续整理、继续演化；适配层重连 |
| F2 | DSH 进程退出 | 无法推理 | 收消息入队，不处理；恢复后补处理 |
| F3 | 模型 API 失败 | 单轮失败 | 重试 → 仍失败则该轮不回，不留半截状态 |
| F4 | 内核崩溃 | 全部中断 | 从持久化恢复：队列、实时记忆、pending 回复 |
| F5 | 磁盘满 | 写失败 | 只读模式：能回，不写；日志与媒体优先清理 |
| F6 | 单文件损坏 | 局部 | 从快照回滚单文件（06 的 4.4） |

**关键原则：故障只影响它所在的那一层。** 渠道断不该影响整理，模型失败不该影响数据；任何跨层传染都是设计错误。

## 三、离线模式的准确含义

「关掉 QQ 它还在」有三种理解，只有一种是我们要的：

| 理解 | 是不是 |
|---|---|
| 进程还活着 | ❌ 只是技术上没退出 |
| 数据还在磁盘上 | ❌ 这是备份，不是存在 |
| **它还在回想、还在变** | ✅ **这才是「在」** |

所以离线 = **没有消息可回，但整理照常进行**。

| 条件 | 离线模式下 |
|---|---|
| 注意力队列为空 | 触发闲暇（D5） |
| 整理会话可运行 | ✅ 照常 |
| 自述照常产生 | ✅ |

## 四、故障期间的消息：过期不回

| 消息年龄 | 处理 |
|---|---|
| < 5 分钟 | 正常回复 |
| 5 分钟 – 2 小时 | **不回复，但记入记忆** |
| > 2 小时 | 不回复，只记一条「错过了」 |

理由：回一条三小时前的消息很奇怪；人看到几小时前的消息不一定回，但会知道有这么回事。此规则与 [26-社交默认值](26-社交默认值.md) 的 T1 相邻但不同——**它不是「不想回」，是「回得不对」**。

**5 分钟 / 2 小时都是经验值，必须进配置**；私聊与群聊可不同（群里过期更快）。

## 五、单轮的事务性：先发送，后记忆

一轮处理包含两件事：**发出去** 和 **记下来**，顺序不能随便。

| 顺序 | 失败时的结果 | 哪种更糟 |
|---|---|---|
| 先写记忆，后发送 | 记忆里有「我说了 X」，实际没说 | **更糟**：角色会引用一句从未发生的话 |
| **先发送，后写记忆** | 发出去了，但没记下来 | 好一些：**说了但忘了** |

选择后者，因为**没发生的事，不该成为记忆**。

落地顺序：

| 步 | 动作 | 分支 |
|---|---|---|
| 1 | 生成回复 | — |
| 2 | 发送 | 否 → 丢弃本轮（不写记忆、不写便签、不更新关系）；是 → 进入第 3 步 |
| 3 | 写记忆 / 便签 / 关系更新 | — |
| 4 | 若第 3 步失败 | 记 trace ERROR，但**不再重试** |

第 4 步不再重试的理由：重试可能造成重复写入，而「少记一条」的代价远小于「记重一条」。

## 六、内核崩溃恢复

靠三样持久化数据：

| 数据 | 文件 | 恢复后 |
|---|---|---|
| 注意力队列 | `runtime/queue.json` | 丢弃过期项，保留未过期 |
| 实时记忆 | `runtime/realtime.log` | append-only，天然安全 |
| 待发送回复 | `runtime/pending.json` | 按 `deliveryId` 核对，已发的移除（WeChatAgent 模式） |

队列必须持久化，否则崩溃期间进来的消息全丢，恢复后角色像失忆。队列项带 `received_at`，恢复时按第四节规则判断是否过期。

队列满时：

| 策略 | 说明 |
|---|---|
| 丢弃最旧的 | 简单，但可能丢掉重要的 |
| 按节点保留各 N 条 | 公平，不让热聊群挤占全部 |
| 丢弃时记一条 | 让角色知道「那段时间太忙，有些没顾上」 |

第三种最有人味：**它会记得自己忙不过来。**

## 七、熔断

DSH 连续失败时不要一直重试，否则会把上游打垮。

| 参数 | 建议 |
|---|---|
| 失败阈值 | 连续 5 次 |
| 熔断时长 | 2 分钟 |
| 半开探测 | 每 30 秒试一次 |
| 期间行为 | 消息只入队，不投递 |

熔断状态要能在 GUI 看到，也要能被管理员 DSH 查到。

## 八、资源耗尽

磁盘满时的清理优先级：

| 顺序 | 清理什么 | 理由 |
|---|---|---|
| 1 | `logs/trace/` | 可删，可重建 |
| 2 | `media/` 过期文件 | 描述还在记忆里（16） |
| 3 | `memory/archive/` | 有月报兜底 |
| 4 | — | **记忆本体与关系绝不清理** |

进入只读模式后：仍能回复（不写记忆）；仍能整理（只读整理，产出丢弃）；GUI 报警。**宁可少记，不可写坏。**

## 九、健康状态

内核维护一个状态对象，供 GUI 与 `status` 工具读取，字段分为 kernel（state / uptime）、channel（state / last_event / reconnects）、dsh（state / last_reply / failures）、storage（state / free）、maintenance（last_light / last_heavy / last_deep）。

`channel: degraded` 而不是 `down`：**还能收、不能发**和**完全断开**是两回事。

## 十、一条原则

**故障不该让角色变得不像它自己。**

- 故障期间不编造（不能推理就沉默，不要用模板假装）。
- 故障期间不遗忘（数据继续保留）。
- 恢复后不假装没事（过期消息不回，但记一笔）。

最差的做法是「降级成规则机器人」——那会让用户觉得「它已经不在了」，正是第一判据要否定的。

## 十一、未决

1. **过期阈值的合理值**：5 分钟 / 2 小时是否合适？私聊与群聊是否要分开？
2. **故障是否该告知对方**：渠道断线时，要不要给对方回一句「他暂时不在」？
3. **熔断期间的整理**：DSH 熔断时整理也停了，这是否可接受？
4. **崩溃后的重复处理**：队列恢复时，如何确保不重复回复已经回过但没来得及出队的那条？
5. **只读模式下的人味**：不写记忆会让连续几轮「断片」，是否有更好的降级方式？
