# 15 · 主体、群与节点

> 上游：[07-关系网络](07-关系网络.md)｜ [10-长期记忆条目](10-长期记忆条目.md)
> 本文件修订 06 / 07 / 10 中的 `contact` 概念。

---

## 一、问题

07 里的关系网络只有 **person**。但角色对「群」也有态度：

- 这个群爱玩梗，那个群只谈工作
- 我在这个群话多，在那个群基本潜水
- 这个群不能说私事，那个群可以

现在这些只能塞进 `overrides[].context` 那个字符串里——**没有结构化的归宿，无法演化、无法查询、无法参与侧面计算**。

这是结构性缺口，不是缺字段。

---

## 二、方案：统一节点，`kind` 区分

| 概念 | 统一为 |
|---|---|
| 人 | `node(kind=person)` |
| 群 | `node(kind=group)` |

不建两套表。理由是**关系机制本身是通用的**：

- 都有亲疏、正式度、信任
- 都有档位、行为集、场合覆盖
- 都能被认领、都能有记忆

差异只在**有哪些维度**，而这恰好是 schema 能表达的（I4：维度是数据）。

---

## 三、一个重要简化：会话 = 节点

之前有三个概念在打架：

| 概念 | 原来长什么样 |
|---|---|
| session | DSH 会话 |
| context | 场合字符串 `"qq:group:同事群"` |
| contact | 人 ID |

现在统一成一条：

> **一个会话，对应一个节点。**

- 私聊 → person 节点
- 群聊 → group 节点

于是：

| 原概念 | 现在 |
|---|---|
| `context` | `node_id` |
| `by_context` 索引 | 就是 `会话 → node_id` |
| 记忆归属 | 按 node |
| 人格侧面 | 按 node |

`overrides[].context` 也不用再是字符串了，直接是 `node_id` 或节点列表——**它有了结构，就能演化。**

## 四、数据结构

```
relations/
├── nodes/
│   ├── person/<node_id>.md
│   └── group/<node_id>.md
├── edges.jsonl
└── _index.json
```

### 4.1 person 节点

```yaml
---
id: n_zhangsan
kind: person
name: 张三
aliases: [老张, 三哥]
identities:
  - { channel: qq, uid: "123456", stability: global, claimed: true }
status: active
first_met: 2026-03-12
tags: [同事, 技术宅]
relation:
  closeness: 0.6
  trust: 0.7
  formality: 0.4
  address_as: "老张"
  boundaries: [不提他的前公司]
  source: observed
---
# 张三
（正文同上，见 07）
```

### 4.2 group 节点

```yaml
---
id: n_qq_123456
kind: group
name: 同事群
identity: { channel: qq, uid: "123456", stability: global }
member_count: 42
status: active
first_seen: 2026-02-01
tags: [工作, 技术]
relation:
  closeness: 0.5          # 我在这个群熟不熟
  formality: 0.8          # 这个群正式程度
  trust: 0.4              # 能说多少私事
  activity: 0.3           # 群活跃度
  boundaries: [不谈薪资, 不发无关节]
  source: observed
---
# 同事群

## 这个群的气氛
（谁主导话题、什么风格、什么时段活跃）

## 我的位置
（话多还是潜水、有没有被接纳）
```

### 4.3 字段差异

| 字段 | person | group |
|---|---|---|
| `aliases` / `address_as` | 有 | 无 |
| `first_met` | 有 | 用 `first_seen` |
| `member_count` | 无 | 有 |
| `activity` 维度 | 无 | 有 |

## 五、schema 按 `kind` 分维度

这正是 I4 的用处：维度是数据，所以可以「按节点类型给不同的维度集」。

```yaml
dimensions:
  - key: closeness
    applies_to: [person, group]

  - key: formality
    applies_to: [person, group]

  - key: trust
    applies_to: [person, group]

  - key: directness
    applies_to: [person]          # 群里不针对单个人调整直接度

  - key: activity
    name: 活跃度
    applies_to: [group]
    levels: [沉寂, 偶发, 活跃, 热闹]
    behaviors:
      沉寂:
        - 不主动发言
      热闹:
        - 可参与接话，但避免刷屏

  - key: safety
    name: 安全度
    applies_to: [group]
    levels: [谨慎, 常规, 放松]
    behaviors:
      谨慎:
        - 不发表情包
        - 不使用网络流行语
```

**新增群专属维度时，不需要改任何代码**——这正是 I4 的红利。

## 六、人与群的关系

边类型新增：

| type | 方向 | 含义 |
|---|---|---|
| `member_of` | person → group | 某人属于某群 |

为什么必须有：角色要知道「张三是我们群的」，说话才有分寸——**在群里提起张三的私事，比在私聊里提起更危险**。

```json
{"from":"n_zhangsan","to":"n_qq_123456","type":"member_of","since":"2026-02-01","confidence":1.0}
```

`member_of` 一般可以从渠道直接得到（群成员列表），不必推测，所以 `confidence` 高。

## 七、记忆归属

```
memory/
├── core/                      # 角色的自我认知、重大事件
├── people/<person_id>/<YYYY-MM>.md
├── groups/<group_id>/<YYYY-MM>.md
├── topics/<topic>/<YYYY-MM>.md
├── journal/
├── archive/
└── _index.json
```

### 7.1 归属规则（单选，不复制）

| 场景 | 归到 |
|---|---|
| 私聊里发生的事 | `people/<id>` |
| 群里发生的事 | `groups/<id>` |
| 跨群的长线主题（如「装修」） | `topics/<topic>` |
| 角色的自我认知、内心 | `core` |

一条记忆**只存一处**。它涉及的人写在 `people` 字段里，靠索引反查（10 的第六节）。

### 7.2 群里的记忆，`people` 字段记谁

群聊的一条记忆可能涉及多个人：

```yaml
people: [n_zhangsan, n_lisi]
```

但要知道「谁说的」——所以条目加一个可选字段：

```yaml
speaker: n_zhangsan        # 这条记忆的主动方
```

## 八、在群里面对某个人，用谁的档位

### 8.1 缺失的输入：在场的人是谁

初版规则是「以人的关系为基础，用群的关系调制，一律取保守侧」。

**这条是错的。** 它等价于假设「这个群里全是陌生人」。

真实情况里还有第三个输入：

| 输入 | 例子 |
|---|---|
| 我对这个人的关系 | 张三是发小，亲近 |
| 这个群的性质 | 技术群，正式 |
| **这个群里有多少我熟悉的人** | 只有 2 个熟人，40 个陌生 |

同一个「技术群」，如果是「我和三个老同事的私密技术群」，说话方式完全不同。

### 8.2 核心：发言面向的是全场

这是整个问题的根：

> **在群里说话，不是对张三说，是当着所有人对张三说。**

所以内容必须对**在场最保守的那个人**也可接受。

但「全场」不等于「全体成员」——一个 500 人的群，实际在说话的只有 5 个人。人在意的是**现在在场的人**，不是名册。

### 8.3 公式：用熟悉度 κ 加权

```
κ = 在场成员中的熟人比例（0–1）

数值层：v = κ · v_person + (1 − κ) · v_group
档位层：按 09 的阈值量化（带滞回）
硬约束：boundaries = 并集（不可被加权掉）
```

| κ | 含义 | 结果 |
|---|---|---|
| 1.0 | 全熟人 | 完全按对他的关系，等于私聊 |
| 0.5 | 一半熟人 | 折中 |
| 0.0 | 全陌生人 | 完全按群的标准 |

### 8.4 一个例子

```
对张三（私聊）：  closeness 0.8, formality 0.2, trust 0.8
这个群：          closeness 0.3, formality 0.9, trust 0.2

κ = 1.0 → closeness 0.8, formality 0.2, trust 0.8   （等于私聊）
κ = 0.5 → closeness 0.55, formality 0.55, trust 0.5 （折中）
κ = 0.0 → closeness 0.3, formality 0.9, trust 0.2   （按群的标准）
```

### 8.5 为什么加权比「取保守侧」好

| 方案 | 问题 |
|---|---|
| 取保守侧 | 熟人之间的私密群也变成公事公办，**行为失真** |
| 纯加权 | 档位离散化之后仍然落到真实档位，**没有「半正式」这种不存在状态** |

关键点：**加权发生在数值层，量化发生在档位层。**

这正是 09 的三段式（数值 → 档位 → 行为集）的用武之处——插值在数值层完成，输出仍是离散档位。

### 8.6 κ 怎么算

```
κ = (最近 N 天发过言、且 trust ≥ 阈值的成员数) / (最近 N 天发过言的成员数)
```

三个细节：

| 细节 | 做法 | 理由 |
|---|---|---|
| 只看**活跃成员** | 不按全体成员算 | 500 人群实际只有 5 人说话 |
| 用 N 天窗口 | 建议 7 天 | 太久远的人不在场 |
| 数据不足时 | `κ = 0` | 宁可保守，不可冒进 |

「熟人」的阈值（`trust ≥ 0.5`）是经验值，应放进 schema 而非代码里。

### 8.7 群的属性从哪来

群的性质（`formality` / `safety` / `activity`）不会凭空出现。四个来源，复用 07 的 `source` 字段：

| 来源 | `source` | 可信度 | 例 |
|---|---|---|---|
| 管理员设定 | `admin` | 最高 | 「这个群不许发表情」 |
| 群成员私下告知 | `stated` | 高 | 张三私聊说「我们那群别开玩笑」 |
| 观察群内发言 | `observed` | 中 | 群里全是工作汇报 |
| 群名称推断 | `inferred` | **低** | 「XX技术交流群」 |

**「私下问熟悉的人」是合法的获取方式**——角色可以在私聊里自然地问「你们那群平时都聊什么」，得到的答案记为 `stated`。

### 8.8 一条约束：推断必须被观察修正

`inferred` 的群属性不能长期主导。

```
群名称推断：这是个技术群 → formality 0.8
观察两周：  群里天天玩梗、发表情包 → formality 应降到 0.3
```

规则：

| 情况 | 处理 |
|---|---|
| 只有 `inferred` | 初始值，标记待验证 |
| 出现 `observed` 且冲突 | **以观察为准**，`inferred` 降权 |
| `stated` / `admin` | 不被观察覆盖（人说的一定算数） |

> **猜来的东西，必须让位给看到的。**

### 8.9 群成员：只对发言者建模

**原则**：不为「群成员名册」建模，只为**发过言的人**建模。

| 做法 | 结果 |
|---|---|
| 拉取完整成员列表 | 依赖渠道能力；大群几千人，多数永不出声 |
| **只对发言者建模** | 数据自然累积；不依赖渠道；每个节点都真实存在过 |

三个好处：

1. **不依赖渠道**：任何渠道都能回答「这条消息是谁发的」
2. **κ 自动可算**：分母就是「发过言的人」，不需要额外统计
3. **顺便得到语言风格**：每个人的发言样本，就是他的语域

#### 建模时机

| 动作 | 谁 | 何时 |
|---|---|---|
| 建 node 骨架（id、身份、首次发言） | 内核（纯规则） | 首次收到该人消息 |
| 建 `member_of` 边 | 内核（纯规则） | 首次在群里发言 |
| 补印象、语言风格 | DSH | 整理时 |

内核只建骨架，DSH 才补内容——符合 I1 / I3 的分工。

#### 残余风险：沉默的旁观者

只对发言者建模，意味着**潜水的人对角色是不存在的**——但他们看得到角色说的话。

这个风险不能靠 κ 解决（κ 的分母里根本没有他们）。

**兜底：trust 设群上限。**

修改 8.3 的公式：

```
closeness = κ · v_person + (1 − κ) · v_group
formality = κ · v_person + (1 − κ) · v_group
trust     = min( κ · v_person + (1 − κ) · v_group ,  trust_group )
```

为什么只有 `trust` 要取 min：

| 维度 | 是否设上限 | 理由 |
|---|---|---|
| `closeness` | 否 | 「亲不亲」是主观感受，可以加权 |
| `formality` | 否 | 「正式不正式」可以加权 |
| **`trust`** | **是** | **「能不能说私事」由在场最不可信的人决定，看不见的人也算** |

这样即使 κ=1（发言的全是熟人），在公开大群里也不会说出不该说的话。

#### 语言风格的用途

「只对发言者建模」顺带得到的东西，不只是 κ。

| 得到什么 | 怎么用 |
|---|---|
| 群的黑话与梗密度 | 影响角色的用词选择 |
| 每个人的说话习惯 | 影响称呼与语气 |

这部分不需要新机制——**qq-bridge 的黑话学习引擎（slang-learner）就是现成的**：

```
群聊消息 → 提取候选黑话 → 人工确认 → 注入 prompt
```

按 G13 的规则，它也要过人工闸门（见 09 的 8.4）。

## 十、未决
