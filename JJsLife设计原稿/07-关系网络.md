## 一、定位：是图，不是表

关系网络的作用是**说明人物关系**，不是登记有谁。它同时面向 AI（据此表现）和管理者（据此审阅、编辑、认领）。

所以它本质上是**图**：

| 成分 | 是什么 |
|---|---|
| **节点** | 人物（角色认识的每个人） |
| **边 A** | 角色 → 人物（角色对他的态度） |
| **边 B** | 人物 ↔ 人物（他们彼此的关系） |

**为什么必须有边 B**：角色要知道「张三和李四是夫妻」，才能在群里说话不出错。这是**社交常识**，不是记忆。

只有边 A 时，角色只理解「我和每个人的关系」，不理解「他们之间的关系」——那它不是在社交，只是在应答。

## 二、真源与分文件判据

### 2.1 真源只有两个

| 真源文件 | 内容 | 数量级 |
|---|---|---|
| `relations/nodes/person\|group/<node_id>.md` | 节点，一个一文件 | 与节点数同阶 |
| `relations/graph.jsonl` | 节点之间的边，一行一条 | 与关系数同阶 |

其余（列表、图、索引、待认领队列）全部**派生**，可随时重建。

### 2.2 分文件的判据：按「谁来维护」分，不按「文件多大」分

| 类型 | 谁维护 | 是否分文件 |
|---|---|---|
| 节点（frontmatter + 正文） | 人 + DSH 都在编辑 | ✅ 一个一文件 |
| 边表 `graph.jsonl` | 只由 DSH / 内核追加，人不逐行改 | ❌ 单文件即可 |
| 索引、列表、图 | 程序生成 | 派生，不进真源 |

理由：

> **人维护的东西要碎，机器维护的东西要整。**

人维护一个大文件会冲突、会误删、会找不到该写在哪；机器维护碎文件则只会让一致性变复杂。

边表若为了「看起来整齐」而分片，就得处理正反双向、跨片查询、部分写入——复杂度全上来，收益接近零。管理员本来也不逐行编辑边表，他看的是**派生视图**。

**规模上界**（现在不处理，但留位置）：节点上千时，`nodes/person/` 目录本身需按 id 前缀分桶。

### 2.3 格式：YAML frontmatter + md 正文

纯 md 难查询，纯 json 难编辑。

| 部分 | 面向 | 用途 |
|---|---|---|
| frontmatter | 管理者 / 程序 | 结构化字段，筛选、统计、批量操作 |
| 正文 | AI | 自然语言描述，「这个人是怎么回事」 |

## 三、节点

`relations/nodes/person/<node_id>.md`

```yaml
---
id: n_01H8XK3M9
kind: person
name: 张三
aliases: [老张, 三哥]
identities:
  - { channel: qq,     uid: "123456",    stability: global,    claimed: true }
  - { channel: wechat, uid: "wxid_abc",  stability: global,    claimed: true }
  - { channel: qq,     uid: "g8842:u17", stability: per-group, claimed: false }
status: active                # active | dormant | archived
first_met: 2026-03-12
last_active: 2026-10-21
tags: [同事, 技术宅, 猫]

relation:                     # 边 A：角色 → 他
  closeness: 0.6              # 亲疏
  trust: 0.7                  # 信任
  familiarity: 0.8            # 熟悉
  address_as: "老张"           # 角色怎么称呼他
  boundaries:                 # 不能碰的话题
    - 不提他的前公司
  source: observed            # stated | observed | inferred | admin

overrides:                    # 场合覆盖（存偏移，不存绝对值）
  - context: "qq:group:同事群"
    closeness: -0.2           # 相对 relation.closeness
    trust: -0.2
    note: "工作场合，保持距离，不提私事"
---
# 张三

## 我眼里的他

（自然语言：性格、习惯、在意什么、相处下来的经验）

## 关系由来

（怎么认识的、关系怎么变化的、有过什么节点性的事）
```

### 3.1 字段为什么这么多

它们不是「登记信息」，是**角色的认知结构**。少一格，角色就少一个判断维度。

三个最容易漏、但必须有的字段：

| 字段 | 不写会怎样 |
|---|---|
| `source` | 角色会把「猜的」当「知道的」说出去 |
| `boundaries` | 角色不知道哪些话题对这个人是禁区 |
| `address_as` | 角色对所有人用同一个称呼，显得不认识人 |

### 3.2 `source` 的可用性规则

| 值 | 含义 | 可用性 |
|---|---|---|
| `stated` | 他亲口说的 | 可直接使用 |
| `observed` | 角色观察到的 | 可使用，措辞谨慎 |
| `knowledge` | 从知识库沉淀的 | 可使用，须标来源 |
| `web` | **网上搜到的** | ⚠️ 必须说「我查到…」，不能说「就是…」（见 [30](30-联网检索.md)） |
| `inferred` | 角色推测的 | **不可当事实使用** |
| `admin` | 管理员设定 | 可使用 |

> **推测出来的关系不能当事实。**

这条必须写死。否则角色会把猜测当真相说出去，而这种错话往往不可挽回。

## 四、人物之间的边

`relations/graph.jsonl`，一行一条：

```json
{"from":"n_zhangsan","to":"n_lisi","type":"colleague","directed":false,"since":"2025-06","confidence":0.8,"evidence":"两人提到同一家公司","note":"不同部门"}
```

| 字段 | 说明 |
|---|---|
| `type` | `colleague` / `friend` / `family` / `couple` / `superior` / `subordinate` / `classmate` / `other` |
| `directed` | 上下级、亲属等不对称关系为 `true` |
| `confidence` | 0–1，推测出来的要低 |
| `evidence` | 依据：对话摘要，或「管理员设定」 |

**为什么不写进人物文件**：若把「张三—李四」写进张三的文件，李四的文件就缺一条，两处必然不一致。

> **边的真源只能有一处。**

## 五、场合覆盖（人格侧面的挂载点）

写在人物条目的 `overrides` 里，自包含——读一个人不需要读别处。

匹配规则：

1. 按 `context` 精确匹配当前会话
2. 无匹配 → 回落到 `relation` 默认值

> **人格侧面不是另一套人格，而是同一份关系在不同场合的投影。**

### 存偏移，不存绝对值

`overrides` 里的数值是**相对基础值的偏移**（如 `-0.2`），不是绝对值（如 `0.4`）。

理由：基础关系会随互动演化。若存绝对值，基础值从 0.6 涨到 0.8 时，这个场合的表现纹丝不动——角色在同事群永远一个样，人格就分裂了。存偏移则场合表现自动跟随。

档位与行为集的具体规则见 [09-人格侧面投影](09-人格侧面投影.md)。

## 六、索引：图的入口

### 6.1 先回答一个疑问：图有没有「快速定位到节点」的能力

没有。这两件事要分开看：

| 操作 | 复杂度 | 说明 |
|---|---|---|
| 已知 id，找他的关系 | O(度数) | 邻接表很快，这是图的强项 |
| 已知名字 / 账号，找 id | O(节点数) | 图不提供，必须遍历 |

图解决的是「**找到之后怎么走**」，索引解决的是「**怎么找到**」。

> **索引是图的入口，不是图的替代。**

### 6.2 四张索引，用途不同

`relations/_index.json`（内核维护，派生但持久化）

| 索引 | 键 → 值 | 谁用 | 频率 |
|---|---|---|---|
| `by_identity` | `渠道:uid` → `node_id` | 内核 | **每轮（热路径）** |
| `by_name` | 名字 / 别名 → `node_id` | AI、管理员 | 中 |
| `by_context` | `node_id`（会话即节点）→ 该节点的成员 | 内核、AI | 每次进入会话 |
| `by_tag` | 标签 → `[node_id]` | 管理员 | 低 |

**`by_identity` 是最关键的一张**：角色每收到一条消息，第一件事就是「这条是谁发的」。这个查询在热路径上，必须 O(1)，不能扫目录。

```json
{
  "version": 1,
  "built_at": "2026-10-23T10:20:00Z",
  "by_identity": { "qq:123456": "n_zhangsan", "wechat:wxid_abc": "n_zhangsan" },
  "by_name":     { "张三": "n_zhangsan", "老张": "n_zhangsan" },
  "by_context":  { "n_qq_123456": ["n_zhangsan", "n_lisi"] },
  "by_tag":      { "同事": ["n_zhangsan", "n_lisi"] }
}
```

### 6.3 一致性规则

| 规则 | 说明 |
|---|---|
| 索引由内核在写入时同步更新 | 纯字符串操作，不涉及推理 |
| 索引永远可丢弃 | 丢了就从真源重建 |
| 不一致时以真源为准 | 索引不是事实 |

> **索引一旦被当成事实，就会出现「文件里没有这个人，但索引里有」的幽灵条目。**

## 七、派生视图（面向管理者）

| 视图 | 内容 | 可重建 |
|---|---|---|
| `relations/_index.md` | 全部人物列表 + 关系概况 | ✅ |
| 关系图 | 可视化网络 | ✅ |
| 待认领队列 | `claimed: false` 的身份 | ✅ |

**原则**：派生视图永远可删可重建。任何写入必须落到真源，不能只改视图。

## 八、各角色的写入权

| 动作 | 谁做 |
|---|---|
| 新身份出现时建 provisional 节点 | 内核（纯规则，不推理） |
| 更新印象、关系值、边 | DSH（整理时） |
| 认领 / 合并 / 拆分 | 管理员 |
| 删除 | 管理员 |

---

## 九、认领：合并发生在关系层，不发生在数据层

> **人物合并 = 关系层的联结，不是数据层的搬迁。**

「认领」只做一件事：让两个 `channel_identity` 指向同一个 `node_id`。

- 不搬任何记忆文件
- 记忆目录仍 per-session（天然符合 scope 隔离）
- 撤销认领 = 断开联结，一切复原

因此「认领」是**轻量、可逆、无副作用**的动作。

### 9.1 四条约束

| 约束 | 理由 |
|---|---|
| 只能管理员发起，不可自动 | 自动推断身份 = 擅自关联，是隐私事故 |
| 必须可撤销 | 认错了要能复原 |
| 必须留审计 | 谁、何时、把谁合并给谁 |
| **冲突时默认拆开** | 宁可分裂，不可错合 |

### 9.2 一条不对称原则

> **宁可让角色认为「这是两个人」，也不能让它认为「这两个账号是同一个人」。**

因为代价不对称：

| 错误 | 后果 | 可修复性 |
|---|---|---|
| 错分（当成两个人） | 记忆分散 | 可修复 |
| 错合（当成同一个人） | 隐私泄露 | 不可修复 |

### 9.3 临时身份

新出现的渠道身份自动建一个**单渠道 node**，标记 `provisional: true`。

- 可正常积累记忆（角色不会失忆）
- 管理员可把它认领到已有 node
- 长期未认领的不自动合并，只标记「待认领」

## 十、标识稳定性

| `stability` | 含义 | 可否跨场合合并 |
|---|---|---|
| `global` | 全局稳定（QQ 号、微信号） | ✅ |
| `per-group` | 仅群内稳定（群成员 ID） | ❌ 只能在本群内识别 |

群内 uid 常为 per-group，跨群合并必然出错。这个字段就是防线。
