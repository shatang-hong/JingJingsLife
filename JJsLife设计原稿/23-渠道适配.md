## 一、定位：一个可插拔的外部进程

适配层不是内核的一部分，是**内核之外、可随时替换的进程**。

```
┌──────────────┐   标准契约   ┌──────────────┐
│  渠道适配器   │◄───────────►│    内核       │
│ （可插拔）    │  HTTP / WS  │              │
└──────┬───────┘             └──────────────┘
       │ 私有协议
       ▼
   QQ / 微信 / …
```

选择「独立进程 + 本地回环通信」而不是「内核内的一个模块」，三个理由：

| 理由 | 说明 |
|---|---|
| 语言无关 | QQ 适配器用 Node（复用 qq-bridge），将来别的渠道可以用别的语言 |
| 崩溃隔离 | 适配器挂了不影响角色整理与记忆 |
| 可热替换 | 换渠道 = 停一个进程、起另一个，内核不动 |

这与 14 的进程隔离原则一致，也与 qq-bridge / WeChatAgent 的做法一致。

## 二、三条不可逾越的边界

### 2.1 内核不感知渠道的

| 不感知 | 说明 |
|---|---|
| 协议 | 是 OneBot 还是 Hook、是 WS 还是 HTTP |
| 账号体系 | QQ 号 / 微信 wxid / 将来的任何 ID |
| 限流与重连 | 多久发一条、断了怎么重试 |
| 分段能力 | 能不能一次发多条 |

### 2.2 适配器不感知角色的

| 不感知 | 说明 |
|---|---|
| 关系与人格 | 它不知道「这是熟人还是陌生人」 |
| 记忆 | 它不知道角色记得什么 |
| **回复节奏** | 延迟多久、分几条，**由内核算** |
| **节点映射** | 谁是谁，由内核查 `by_identity` |

### 2.3 会话 → 节点的映射归内核

15 说「会话 = 节点」，但**转换动作在内核**：

```
适配器只提供 (channel, uid)  →  内核查 by_identity  →  node_id
```

理由：映射依赖关系索引，那是内核的资产。适配器若做这件事，就不再是薄层。

---

### 2.4 第四条边界：不依赖第三方渠道插件

**决策：适配层自研，不建立在任何第三方 IM 插件之上。**

背景：DSH 生态里有个 `dsh-im`（统一 IM 桥核心），看起来正好是「渠道适配」的现成答案。调研后否决。

#### 它是什么

| 项 | 内容 |
|---|---|
| 定位 | 统一 IM 桥**核心**：会话映射、命令、渲染、通知总线、审批管理 |
| 内置渠道 | **只有 `MockChannel`**，没有任何真实 IM 通道 |
| 真实渠道 | 需第三方实现 `send()` 契约后自行注册 |
| 使用方向 | **人 → DSH**：远程指挥、通知、审批卡片 |

#### 三条否决理由

| # | 理由 | 说明 |
|---|---|---|
| 1 | **没有真实通道** | 内置只有 MockChannel。所谓「接入」，等于自己写通道——那不如直接写适配器 |
| 2 | **方向相反** | 它是「人指挥 DSH」（`/approve`、审批、通知），我们要的是「角色参与群聊」 |
| 3 | **依赖即失控** | 角色是长期存在的，插件随 DSH 版本变化 |

第 3 条是根本：

> **角色活得比插件久。** 把命脉交给一个会随上游变化的东西，等于给角色定了一个短寿命。

这与 [22](22-运行与治理.md) 的「凡持有角色级配置的组件不能跨角色共享」是同一种谨慎：
**角色依赖的外部组件，必须可替换，而不是被依赖。**

#### 但它的入站契约值得借鉴

`dsh-im` 的 `dispatchInbound` 形状：

```js
{ platform, chatId, userId, text, msgId, chatType }
```

与本文 4.1 的 `KernelMessage` **几乎同构**。

这说明「统一 IM 桥」这个抽象方向是对的——不是我们想歪了。

> **借鉴契约，不依赖实现。**

#### 一个反向用途（不是现在）

`dsh-im` 更适合做**管家通道**：管理员用手机给角色发 `/status`、批准候选、接收告警。

那是管理入口（[14](14-管理入口.md)）的事，不是渠道适配（23）的事。**两者不要混。**

## 三、能力声明（模块化的关键）

**内核不能假设所有渠道都一样。**

QQ 支持引用和撤回，微信不支持「正在输入」，某些渠道一次只能发一条——这些差异如果硬编码进内核，换渠道就要改内核。

所以适配器启动时必须**声明自己的能力**：

```yaml
capabilities:
  text: true
  image: true
  sticker: true
  voice: false
  file: false
  recall: true
  typing: false            # 是否支持「正在输入」
  segmented_send: true     # 能否连发多条气泡
  max_text_length: 4500
```

### 3.1 能力直接影响输出策略

| 能力 | 缺失时的降级（由内核决定） |
|---|---|
| `segmented_send: false` | 把分段拼回一条，用换行代替气泡间隔 |
| `sticker: false` | 行为集里 `sticker_density` 强制为「无」 |
| `typing: false` | 只保留 `delay_ms`，不显示输入状态 |
| `max_text_length: 4500` | 超长时按语义切分 |

> **能力声明让内核保持通用，同时不假装渠道是无限的。**

这是模块化真正的着力点——不是「接口长得一样」，而是「**能力可查询、差异可降级**」。

### 3.2 未声明即不支持

规则：**capabilities 里没有的项，一律视为不支持。**

不采用「默认支持、出错再说」，因为那会让内核在运行中途才发现问题（而消息已经发出去了）。

## 四、契约：四个接口

### 4.1 入站（适配器 → 内核）

```
POST /ingest
{
  channel: "qq",
  conversation_id: "123456",     // 私聊=对方QQ号，群聊=群号
  is_group: true,
  sender_uid: "7890",            // 群里是谁说的；私聊时等于 conversation_id
  sender_name: "张三",
  message_id: "abc123",
  timestamp: 1697000000,
  text: "今天天气怎么样",
  media: [ { kind: "image", ref: "sha256:…", size: 102400 } ],
  quote: null                    // 引用回复的原消息 id
}
```

注意 `conversation_id` 与 `sender_uid` **必须分开**：

- 私聊：两者相同
- 群聊：前者是群，后者是人

不分开，内核无法判断「这是群里某个人说的」还是「私聊」。

### 4.2 出站（内核 → 适配器）

```
POST /send
{
  conversation_id: "123456",
  segments: [ "今天还行", "你那边呢" ],
  media: [],
  delay_ms: 1800,          // 由内核算（21 的第三节）
  reply_to: null
}
```

**`segments` 与 `delay_ms` 由内核生成，适配器照做。**

适配器不该自己决定「切几段」「等多久」——那是关系档位的产物，属于角色的分寸。

### 4.3 健康（内核 → 适配器）

```
GET /health
→ { state: "ok" | "degraded", last_event_at, reconnects, capabilities }
```

`degraded` 与 `down` 要分开——能收不能发和完全断开是两回事（17 的第九节）。

### 4.4 能力（内核启动时拉取一次）

```
GET /capabilities
→ 见第三节
```

## 五、QQ 适配器：现在的唯一实现

### 5.1 形态

```
QQ 客户端
    ↓
SnowLuma（OneBot v11 网关）
    ↓ WebSocket
┌─────────────────────┐
│   QQ 适配器          │
│  · OneBot 事件解析    │
│  · 标准消息转换       │
│  · action 调用        │
└─────────────────────┘
    ↓ 标准契约
   内核
```

### 5.2 可复用的部分

| 来源 | 复用 |
|---|---|
| qq-bridge | `snowluma-conn.js`（端点发现、token 自动更新、健康信号） |
| qq-bridge | 消息标准化（文本/图片/表情/引用/合并转发的解析） |
| qq-bridge | `md-to-plain.js`（出站格式转换） |
| WeChatAgent | `normalize.js` 的标准化思路、反循环去重 |

### 5.3 不要复用的部分

- `bridge.js` 的任何角色逻辑（会话路由、人格注入、回复决策）——那正是内核要接管的部分
- 白名单与安全审计：**移到内核**，因为那是角色级策略，不是渠道级

## 六、为什么现在只做 QQ

| 渠道 | 状态 | 原因 |
|---|---|---|
| **QQ** | ✅ 做 | SnowLuma 提供稳定的 OneBot 接口，链路成熟 |
| 微信 | ❌ 不做 | 需要 DLL 注入，随微信版本失效，维护成本高 |

但注意：

> **只做 QQ ≠ 只设计 QQ。**

接口按通用契约设计（第三节的能力声明就是为此），将来接微信只需新写一个适配器进程，内核一行不改。

这也是把「能力声明」放进契约的原因——它让「将来」这件事有具体的技术形态，而不是一句愿望。

---

## 七、一个容易被忽略的边界：白名单在哪

原项目里白名单在桥接层（qq-bridge 的 `config.json`）。

这里要移进内核，理由：

| 白名单是什么 | 归属 |
|---|---|
| 「这个群允许角色说话」 | 角色的社交选择 → 内核 |
| 「这个频道能不能连」 | 渠道的连接配置 → 适配器 |

两者容易混。判据：**与「角色愿不愿意」有关 → 内核；与「技术上通不通」有关 → 适配器。**

## 八、未决

1. **单账号还是多账号**：一个适配器进程能接多个 QQ 号吗？倾向一个进程一个账号。
2. **`/ingest` 的背压**：内核处理不过来时，适配器是丢消息还是阻塞？
3. **媒体文件的传递方式**：`ref` 是 hash，但适配器拿到的是本地文件路径，谁负责搬运到 `character/media/`？
4. **撤回的双向同步**：用户撤回一条消息，内核的记忆要不要跟着删？
5. **能力协商的时机**：只在启动时拉一次，还是每次重连都拉（换网关后能力可能变）？
