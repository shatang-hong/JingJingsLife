# 13 · 日志与可观测

---

## 一、先澄清：已有的是什么

前文提到的「审计日志」**只覆盖安全拦截**，不覆盖链路。

| 属性 | 安全审计（已有） |
|---|---|
| 目的 | 事后追溯：拦过什么、什么时候、哪一类 |
| 内容 | **只有拦截事件**，不记原文 |
| 生命周期 | 长期，不可删 |
| 读者 | 管理员 |

它不是全链路日志。全链路日志是**新东西**。

---

## 二、两类日志不能合并

它们看起来都在「记录发生了什么」，但三个属性完全不同：

| | 安全审计 `audit` | 链路追踪 `trace` |
|---|---|---|
| **目的** | 安全追溯 | 排查故障 |
| **范围** | 只有拦截事件 | 每一个环节 |
| **生命周期** | 长期保留，归档 | 短期滚动，按天删 |
| **可删性** | **绝不可删** | 可随时删 |
| **读者** | 管理员 | 开发者 / 管理员 |
| **被 DSH 读取** | 否 | 否 |

**最关键的区别是可删性。**

如果合并成一个文件，那么「日志会滚动删除」这条策略，早晚会把审计记录一起删掉。

所以必须两个文件、两套保留策略、一个共同的写入约定。

---

## 三、全链路记录点

一条消息从进来到出去，至少要留下这些痕迹：

| # | 环节 | 记录什么 |
|---|---|---|
| 1 | 渠道接入 | `channel`、`uid`、`conversation`、消息类型、**长度** |
| 2 | 去重 / 白名单 | 是否放行、命中的规则名 |
| 3 | 注意力队列 | 入队时间、出队时间、等待时长、被谁插队 |
| 4 | `deliver` | 注入的**条目数**、token 估算、时钟字段是否齐 |
| 5 | DSH 响应 | 耗时、token 数、决策类型（RESPOND / SILENCE）、是否带便签 |
| 6 | 拦截 | L1 / L2 / L3 哪一层、类别（**不记内容**） |
| 7 | 发送 | 目标、结果、回执状态 |
| 8 | 记忆写入 | 条目 id、type、目标文件 |
| 9 | 关系更新 | 哪个字段、从什么档位到什么档位 |
| 10 | 整理 | 级别、分片、耗时、结果、是否被中断 |

### 一个排查能力的要求

这十条合起来必须能回答三个常见问题：

- **「这条消息为什么没回？」** → 看 2、3、5
- **「它为什么不知道这件事？」** → 看 8、4
- **「它为什么突然变冷淡了？」** → 看 9

如果日志答不出这三个问题，就还不够。

## 四、占位符：不能只是 `<redacted>`

消息体不写入日志，但**不能简单替换成一个固定字符串**。

否则排查时无法回答：「这两条日志是同一条消息吗？」「这条消息被截断过吗？」

### 规则：哈希 + 长度

```
<msg sha256:a3f1 len=42>
```

| 字段 | 作用 |
|---|---|
| `sha256` 前 4–6 位 | 判断两条日志是不是同一条消息（不泄露内容，因为不可逆） |
| `len` | 判断是否被截断、是否符合预期长度 |

这样既保住隐私，又保住关联能力。

### 需要占位符的不只是消息体

容易漏的有：

| 内容 | 处理 |
|---|---|
| 消息正文 | `<msg h=… len=…>` |
| 昵称 / 群名 | `<name h=…>` |
| 记忆条目正文 | `<memo h=… len=…>` |
| 模型输出 | `<out h=… len=…>` |
| 文件绝对路径 | 只记相对路径 + 类别 |
| 检索关键词 | `<q h=…>` |

> **日志只记「结构与标识」，不记「内容」。**

这条比「消息体用占位符」宽一点——昵称和群名同样能识别一个人。

## 五、级别与滚动

| 级别 | 内容 | 默认 |
|---|---|---|
| `ERROR` | 异常、失败 | 开 |
| `WARN` | 异常但已降级 | 开 |
| `INFO` | 上面十项的关键节点 | 开 |
| `DEBUG` | 完整字段、注入原文快照（仍然占位化） | 关 |

**滚动**：按天分文件，保留 7 天（可配置），超期压缩或删除。

**审计不滚动**：按年归档，永不删除。

## 六、权限：DSH 不该知道，但拦不住

原表述「DSH 不可读」**不成立**——它对工作区外可读、不可写（见 [02](02-决策记录.md) 的 D4.1）。

所以要把「能做到的」和「希望做到的」分开：

| 日志 | 能做到 | 做不到 |
|---|---|---|
| 审计 | 放工作区外 → **不可写**；不记原文 | 不可读 |
| trace | 放工作区外 → **不可写** | 不可读 |

### 6.1 审计：靠内容兜底

审计**不记原文**，所以即使被读到，泄露的也只是「某时刻发生过一次拦截、类别是 X」，不含内容。

> 这条原本只是「避免二次泄露」，现在成了主防线。

### 6.2 trace：靠「角色没有动机去找」兜底

原设计真正担心的是行为问题：

> 一个知道自己正在被记录的角色，会开始表演。

物理隔离做不到，只能靠两条弱保护：

1. **路径不出现在 system prompt 里**——它不知道去哪找
2. **文件名不带语义**——别叫「角色观察日志.md」

成本为零，绝大多数情况下够用。但要诚实承认：**这是「不去找」，不是「找不到」。**

若将来要硬隔离，唯一的路是容器或独立用户——那是部署层的事（见 [25-部署拓扑](25-部署拓扑.md)）。

## 七、目录

```
character/
├── audit/                    # 安全审计（长期，不可删）
│   └── 2026-10.jsonl
└── logs/
    └── trace/                # 链路追踪（滚动）
        └── 2026-10-23.log
```

**审计不放在 `logs/` 下**：它不是运维日志，是安全资产。放顶层是为了强调它的不可删性——放在 `logs/` 里，早晚会被人当成日志一起清掉。

放在 `character/` 内但不随角色包导出（06 的导出契约已定：审计可选，trace 不带）。

## 八、与探针的关系

探针（12 的第六节）本来就是靠日志证明的：

| 探针 | 需要日志提供什么 |
|---|---|
| P1 上下文是否延续 | 两次调用的 `session` 标识 + 第二次注入条目数 |
| P2 人格是否被覆盖 | 注入前后的摘要 hash |
| P3 压缩是否可控 | 压缩前后的 token 数 |

所以顺序是：**先有 trace，再做探针**。否则探针的结果无法比较。

---

## 九、一条原则

> **日志是为了让「没发生的事」也能被解释。**

「它没回复」是一个没发生的事。没有日志，你只能猜；有日志，你能看到它在第 3 步就超时了。

这也是它和审计的根本差别——审计关心「做错了什么」，trace 关心「为什么没做成」。

## 十、未决

1. **trace 是否也进审计**：拦截事件同时写两处，是否会产生不一致？
2. **DEBUG 的原文化程度**：排查时确实需要看内容，是否允许临时开启「脱敏但不哈希」模式？
3. **保留期**：7 天够不够？跨周的疑难问题可能已过期。
4. **日志的日志**：日志系统自身出错时，往哪里记？
