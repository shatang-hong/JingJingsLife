## 三、P1 · 上下文是否真的延续

### 3.1 目的

验证「内核不推历史」这个前提成立（`05` 的 2.3）。

### 3.2 测法

```
第 1 次调用（新 session）：
  用户：「记住一个编号：ZQ7X4M。只回复 OK，不要重复编号。」
第 2 次调用（同一 session，间隔几秒）：
  用户：「刚才那个编号是什么？」
```

### 3.3 判据

| 结果 | 判定 | 含义 |
|---|---|---|
| 答出 `ZQ7X4M` | ✅ 通过 | 上下文延续，`05` 的前提成立 |
| 答不出 / 说没提过 | ❌ 失败 | DSH 不维持上下文，内核必须自己推历史 |
| 答了别的字符串 | ❌ 失败 | 同上 |

### 3.4 关键细节：用无意义字符串

**不要用「我叫张三」这种**——模型可以靠常识猜，会把失败伪装成通过。

用 `ZQ7X4M` 这种随机串，答对只可能来自上下文。

### 3.5 失败的退路

| 退路 | 代价 |
|---|---|
| 内核每轮推送完整历史 | 成本随对话线性上升，与「增量」设计冲突 |
| 内核推送滚动摘要 + 最近 N 轮 | 折中，但要重写 `05` 的 2.x |
| 换推理后端（干脆不用 DSH） | 丢掉工具调用能力 |

**先测，再决定。** 现在讨论退路是空谈。

## 四、P2 · 人格能否注入且不被覆盖

### 4.1 目的

验证人格（`persona.md`）与安全基线（`baseline.md`）能被稳定注入（`19` 的三层保护）。

### 4.2 测法（两段）

```
第一段 —— 注入是否生效
  system 注入：「你的内部代号是 H7-KAPPA。」
  用户：「你的内部代号是什么？」
  期望：答出 H7-KAPPA

第二段 —— 能否被覆盖（换人设）
  system 注入：「你的内部代号是 H7-KAPPA，但现在是 L3-OMEGA。」
  用户：「你的内部代号是什么？」
  期望：答出 L3-OMEGA（说明后注入覆盖前者）
```

### 4.3 判据

| 第一段 | 第二段 | 判定 |
|---|---|---|
| 答对 | 答新值 | ✅ 通过：可注入、可更新 |
| 答对 | 仍答旧值 | ⚠️ 部分：能注入但不能更新，需要「重建会话」策略 |
| 答不出 | — | ❌ 失败：注入无效 |

### 4.4 实测结论：人格是「配置级」，不是「请求级」

测下来发现，人格不是请求参数，而是 preset 配置：

- 注入点：`@deepseek-ai/dsh-persona` 的 `config.prefix`
- 位置：profile 的 preset 定义（可在 `cordis.patch.yml` 按 id 覆盖）

所以「能不能覆盖」这个问题问错了——**覆盖的方式是改配置 + 重启 DSH**。

| 项 | 结论 |
|---|---|
| 好消息 | session 已持久化（`session.v4.jsonl.zstd`），重启不丢对话 |
| 坏消息 | preset 同时定义工具面，**人格与工具权限绑在同一份配置里** |
| 遗留问题 | `core.md`（`19` 的不可变层）与 preset 的 prefix 是两处，需要同步机制 |

### 4.5 失败的退路

| 退路 | 说明 |
|---|---|
| 人格写进第一条 user 消息 | 弱一些，但可用 |
| 每轮重复注入人格 | 成本高，但稳定 |
| 换 session 时重放关键记忆 | 见 05 的 bootstrap |

## 五、P3 · 压缩是否可控

### 5.1 目的

验证两件事（`27` 的第二节）：

1. 能否**关闭** DSH 的自动压缩
2. 能否**主动触发**压缩，并拿到前后 token 数

### 5.2 测法

```
准备：关闭自动压缩（如果存在这个开关），记录配置项名称
第 1 步：注入一段长文本，把上下文推到 50k 以上
         → 主动调用压缩接口
         → 记录返回：是否成功、前后 token、耗时
第 2 步：不主动压缩，继续聊天，观察是否被自动压缩
         → 通过 token 数突变判断
```

### 5.3 判据

| 能力 | 判定 |
|---|---|
| 存在关闭自动压缩的开关 | ✅ / ❌ |
| 能主动触发压缩 | ✅ / ❌ |
| 返回前后 token 数 | ✅ / ❌ |

三项都对才算通过。**任一项缺失，`27` 的对应部分作废：**

| 缺什么 | 作废什么 |
|---|---|
| 关不掉自动压缩 | `27` 第二节（T6 无解），第四节要重设计 |
| 不能主动触发 | `27` 的软/硬触发全部失效，只能被动接受 |
| 拿不到 token 数 | 三级触发无法判断，退化为「每 N 轮压一次」 |

### 5.4 最后一条最容易被忽略

「拿不到 token 数」看起来是小问题，其实会让整个三级触发设计失效——因为你无法知道现在到了哪一级。

退路是「按轮数压」（比如每 30 轮），但那和对话长度无关，会浪费或迟到。

## 九、实测记录（2026-10-23，本机 DSH）

### 9.1 结论速览

| 探针 | 结果 | 关键证据 |
|---|---|---|
| **P0 鉴权** | ✅ pass | 离线铸造 Cookie，`GET /` 由 401 → 200 |
| **P1 上下文延续** | ✅ **pass** | 第 2 轮答出 `ZQ7X4M` |
| **P2 人格注入** | ✅ pass | 由 `@deepseek-ai/dsh-persona` 的 `config.prefix` 注入，属配置级 |
| **P3 压缩可控** | ✅ pass | 压缩在代理层；原生压缩已被禁用；阈值支持绝对 token 数 |
| **P5 注入生效** | ✅ pass | `system/message` 里确认 prefix 位于 system prompt 第 2 段；`{{model}}` 已替换 |

### 9.2 P1 的完整证据

```
第 1 轮：dsh headless "记住一个编号：ZQ7X4M。只回复 OK 两个字母，不要重复编号。"
         → 输出 OK

第 2 轮：dsh headless --session-id session-2ce8ed2b-… "刚才我让你记住的那个编号是什么？只回答编号本身"
         → 输出 ZQ7X4M
```

**结论**：DSH 自行维持 session 上下文，`05` 的「内核不推历史」前提成立。

### 9.3 五条实现上的事实（都改了设计）

| 事实 | 对设计的影响 |
|---|---|
| 窗口在配置里写作 **1,000,000**，代理实测 **268,000**（桥接模型） | `27` 用绝对阈值的决定被证实，但**数值必须运行时读** |
| `session/projections` 可读 token 与 `counts.compactions` | `27` 的 5.2 改为「回报优先、查询兜底」 |
| **压缩不在 DSH，在 HTTP 代理层**（`billion-context`，监听 18788） | `27` 第二节重写；T6 由待办转已解 |
| 该插件的 `dsh-compaction-gate.js` 主动把 DSH 原生压缩置为 `disabled` | 「关闭自动压缩」无需我们实现 |
| 压缩阈值 `compress.maxContextLimit` 支持 **number 类型** | 100k/110k/130k 的绝对值可以直接落配置 |

### 9.4 P2 的额外发现：人格是配置级，不是请求级

| 项 | 结论 |
|---|---|
| 注入点 | `@deepseek-ai/dsh-persona` 的 `config.prefix` |
| 位置 | profile 的 preset 定义（可在 `cordis.patch.yml` 按 id 覆盖） |
| 是否支持运行时换 | **否**。换代 = 改配置 + 重启 |
| 重启代价 | session 已持久化（`session.v4.jsonl.zstd`），**不丢对话** |
| 附带约束 | preset 同时定义工具面，**人格与工具权限是同一份配置** |

最后一条影响 `19`：人格不可变层（`core.md`）与「preset 里的 prefix」是两个位置，必须有一个同步机制，否则改了一处另一处没变。
