# 11 · 整理会话

> 上游：[04-时钟与闲暇](04-时钟与闲暇.md)（D5）｜ [05-内核接口形状](05-内核接口形状.md)（`idle`）｜ [10-长期记忆条目](10-长期记忆条目.md)

---

## 一、它不是后台任务

**常见做法**：一个定时的后台 job，跑数据清洗。

**这里的做法**：角色在没人说话的时候，**自己回想一会儿**。

差别不是修辞，它决定三件事：

| | 后台任务 | 回想 |
|---|---|---|
| 时间 | 定时 | 闲暇（D5） |
| 中断 | 不该被打断 | **必须能被消息打断** |
| 产物 | 更新后的数据 | 数据 + **一段自述** |

所以它是一个**会话**（maintenance session），不是一个 worker。

---

## 二、四个等级

| 级 | 频率 | 范围 | 回答的问题 |
|---|---|---|---|
| **L0 轻** | 每次闲暇 | 实时记忆 | 「刚才那些，有什么该记住的？」 |
| **L1 重** | 每天 | 单个会话的上下文 | 「这段对话，还有什么值得留的？」 |
| **L2 深** | 每周 | 本周全部记忆文件 | 「这一周，发生了什么？」 |
| **L3 月** | 每月 | 上月全部（含归档） | 「这一个月，我变了没有？」 |

### 等级的差别不是工作量，是「视野」

> **日看事件，周看片段，月看趋势。**

这是为什么月度最高级——只有它能看到**变化**本身，而不只是事件堆叠。日和周看到的都是"发生了什么"，月看到的才是"什么在变"。

---

## 三、L0 轻整理

**触发**：每次闲暇。

| 动作 | 谁做 | 说明 |
|---|---|---|
| 归档实时记忆 | **DSH** | 把 `runtime/realtime.log` 的事实便签沉淀为长期记忆条目 |
| 扫 `promise` | **DSH** | 未完成项进清单，过期的升格为「欠着的事」 |
| 清空 / 轮转 | **内核** | 仅在 DSH 声明「归档完成」后执行 |

**清空必须是内核的动作**：DSH 只负责说「我归档完了」，真正删日志的是内核。

这样即使 DSH 误报，也有一层可追溯的边界——与 17 的「先发送后记忆」是同一个思路：**不可逆的动作，交给不会误判的一方。**

成本低，可以每次闲暇都做。

---

## 四、L1 重整理：落盘 → 压缩

**触发**：每天一次，或会话上下文接近阈值。

### 4.1 关于「清理上下文」的可控性

先回答一个现实问题：**能不能精确控制压缩时删掉哪些细节？**

**不能。** 压缩是 DSH 内部行为，模型自己决定保留什么，我们只能控制：

| 可控 | 不可控 |
|---|---|
| 什么时候压（触发时机） | 具体删掉哪一句 |
| 压到什么程度（阈值） | 保留的措辞 |
| 压之前要求它保留什么（指令） | 是否真的照做 |
| 压之后检查关键条目还在不在 | — |

所以压缩的结果是**概率性**的。

### 4.2 但顺序可以让它变安全

关键在这一步的顺序：

```
1. 先落盘：把重要内容写成记忆条目（外化）
2. 再压缩：丢掉上下文里的细节
3. 后校验：对比「压缩前声明的要点」是否都已落盘
```

> **不是控制压缩删什么，而是让重要的东西在压缩前就已经不在上下文里了。**

压缩丢掉的，只剩「本来就没打算留的」。这样"不可控"就不再是风险。

这也正好是你说的「记忆处理方案」：**细节的流失不是发生在记忆里，而是发生在还没成为记忆的那部分。**

### 4.3 L1 的动作清单

| 动作 | 说明 |
|---|---|
| 选取待整理会话 | 只处理「上下文接近阈值」或「今日有互动」的，不做全量 |
| 落盘 | 把本轮值得留的内容写成记忆条目 |
| 压缩 | 调 DSH 压缩，丢掉细节 |
| 校验 | 检查声明的要点是否均已落盘 |
| 合并记忆 | 同一分片内零散小事合并为一条 |
| 更新关系 | 按近期互动调整 `relations/` 数值与档位 |

> 「上下文接近阈值」的阈值与压缩期间的消息处理，见 [27-上下文压缩](27-上下文压缩.md)。
>
> 注意区分：**本节的「压缩」指的是 DSH 会话上下文压缩，不是记忆整理。** 前者排他、有超时；后者的可中断性见 05 的 4.3。

### 4.4 一个节流

不要一次处理所有会话。只处理**上下文接近上限**的那些——否则每天的整理成本会超过聊天本身。

## 五、L2 深整理：整理本周 + 写周记

**触发**：每周一次（建议周末夜间）。

| 动作 | 说明 |
|---|---|
| 汇总本周记忆文件 | 把本周产生的条目收拢 |
| 归档本周 | 移入 `memory/archive/YYYY-MM/YYYY-MM-DD.md` |
| 人格微调 | L1/L3 层演化，写入前过基线校验 + 快照 |
| 知识沉淀 | 通用性内容移入 `knowledge/notes/` |
| **写周记** | 生成 `memory/journal/week/YYYY-Wnn.md` |

### 5.1 周记的约束

| 约束 | 值 |
|---|---|
| 字数上限 | **3000 字**（硬上限，超出截断并记警告） |
| 字数下限 | 0 |
| 内容要求 | **无** |
| 可以不写吗 | **可以** |

**为什么允许空着**：

有些周没什么可说的。如果强制每周都要写出点什么，角色会开始编——**编出来的周记比空白更假**。

空白的周记本身也是信息：「这周没什么值得记的」。

### 5.2 周记写什么（不给要求，只给方向）

不规定格式，但可以自由写成这样：

> 这周小明提到换工作的事，说了两次。
> 老张还是老样子，猫的照片一天三张。
> 我自己好像有点急，回话比平时快。

**它不需要总结、不需要结论、不需要积极向上。** 它只需要是「这一周对我来说是什么样」。

## 六、L3 月度整理：最高级

**触发**：每月初，整理上一个自然月。

### 6.1 为什么它最高级

日整理看的是**事件**，周整理看的是**片段**，只有月度有足够长的视野看到**变化**：

| 只有月度能看到的 | 例子 |
|---|---|
| 关系的**趋势** | 和小明这个月聊得比上月少了三分之一 |
| 互动的**模式** | 这个群只在深夜活跃 |
| 人格的**漂移** | 我最近说话变短了 |
| 维度的**不足** | 反复出现「明明是朋友却要客气」的情形 |

这些在日和周的尺度上都是噪声，在月的尺度上才是信号。

### 6.2 建议的动作清单

| # | 动作 | 为什么只能月做 |
|---|---|---|
| 1 | **跨主体归纳** | 单周内一个人可能只出现一次，跨月才看得出关系走向 |
| 2 | **趋势计算** | `closeness` 的月均值与环比，而非单次值 |
| 3 | **真正的遗忘** | 只有月度有足够视野判断「这件事是不是真的不重要」，据此标记 `deprecated` |
| 4 | **维度演进提议（L2）** | 需要跨月模式才能判断「现有维度解释不了」 |
| 5 | **归档封存** | 上月所有记忆移入归档区，生成月报 |
| 6 | **数据体检** | 索引重建、孤儿条目、关系值与实际互动明显不符的项 |
| 7 | **写月报** | `memory/journal/month/YYYY-MM.md` |

### 6.3 三条最关键

如果只能保留三条，是 **3、4、6**：

- **3 真正的遗忘**：日和周都不敢忘，只有月度敢。因为只有它见过足够多的重复，能判断「这件事后来再没被提起过」。
- **4 维度演进**：这是 I4 的 L2 层，唯一触发点在这里。
- **6 数据体检**：一个月的读写之后，索引、关系值、孤儿条目必然出现偏移，需要一次对账。

### 6.4 月报

同样是「无内容要求 + 字数上限」（建议 3000 字），但视角比周记高一层：

> 这个月大致是这样：前半月很闲，后半月忙起来。
> 和小明的关系好像淡了一点，但不是坏事。
> 我开始觉得对老张不用那么客气了。

## 七、归档目录结构

### 7.1 活动区与归档区分离

| 区 | 组织方式 | 原因 |
|---|---|---|
| **活动区** | 按主体（人 / 主题）+ 月 | 整理时需要按人聚合 |
| **归档区** | **按时间（年-月 / 日）** | 回溯时需要按时间翻阅，且不再频繁访问 |

### 7.2 目录

```
memory/
├── core/
│   └── 2026-10.md                    # 自我认知、重大事件
│
├── people/
│   └── n_zhangsan/
│       └── 2026-10.md                # 活动：按人 + 月
│
├── groups/
│   └── n_qq_123456/
│       └── 2026-10.md                # 活动：按群 + 月
│
├── topics/
│   └── 装修/
│       └── 2026-10.md
│
├── journal/                          # 角色的自述
│   ├── week/
│   │   └── 2026-W43.md
│   └── month/
│       └── 2026-10.md
│
├── archive/                          # 归档：按时间
│   └── 2026-10/
│       ├── 2026-10-01.md
│       ├── 2026-10-02.md
│       ├── ...
│       └── 2026-10-summary.md        # 月报副本
│
└── _index.json                       # 派生索引（覆盖活动区 + 归档区）
```

### 7.3 命名规则

| 对象 | 命名 | 例 |
|---|---|---|
| 活动记忆 | `<YYYY-MM>.md` | `2026-10.md` |
| 归档记忆 | `<YYYY-MM-DD>.md` | `2026-10-23.md` |
| 周记 | `<YYYY>-W<nn>.md`（ISO 周） | `2026-W43.md` |
| 月报 | `<YYYY-MM>.md` | `2026-10.md` |

统一用 `YYYY-MM-DD` 是为了排序天然正确，不需要额外索引。

### 7.4 归档时保留什么

条目里的 `people` / `session` / `type` 字段**原样保留**。

所以归档后虽然按天组织，仍然可以「找出所有关于小明的记忆」——靠索引，不靠目录。

> **目录决定怎么翻，索引决定怎么找。**

### 7.5 归档不可逆

归档后不再回写活动区。

理由：如果归档还能改，就永远不知道该信哪一份。归档是"已经想过一遍的东西"，它的价值在于**固定**。

## 八、执行顺序（有依赖，不能乱）

```
L0  归档实时记忆
      ↓
L1  落盘 → 压缩上下文 → 校验 → 合并 → 更新关系
      ↓
L2  汇总本周 → 归档 → 人格微调 → 知识沉淀 → 写周记
      ↓
L3  跨主体归纳 → 趋势 → 遗忘标记 → 维度提议 → 封存 → 体检 → 写月报
      ↓
     索引重建
```

**两个必须注意的位置**：

1. **`promise` 要在合并之前扫**。合并会把多条记忆压成一条，承诺的截止条件很可能被压扁。先扫出来单独留存。
2. **压缩在落盘之后**。反过来就丢了。

## 九、分片：一次只能想一个人

整理需要读该分片的**全部**记忆。一次读全局装不下——这是物理上限，不是优化问题。

但它恰好符合回想的样子：

> **人在回忆时，也是一次只想一个人、一件事。**

不会有人「同时回想所有人」。分片不是妥协，是**回想本来的形态**。

### 9.1 各等级的分片方式

| 级 | 分片单位 |
|---|---|
| L1 | 单个会话 |
| L2 | 本周的单个人 / 主题 |
| L3 | **按人跨全月**（一个人一月一片） |

L3 的分片最大，所以月度整理必须能分多次跑完。

### 9.2 进度必须落盘

```yaml
# runtime/maintenance.json
last_light: 2026-10-23T22:10:00+08:00
last_heavy: 2026-10-23T03:00:00+08:00
last_deep:  2026-10-20T03:00:00+08:00
last_month: 2026-10-01T03:00:00+08:00

shards:
  n_zhangsan: { level: monthly, last_done: 2026-10-23T03:20:00+08:00, cursor: null }
  n_lisi:     { level: weekly,  last_done: 2026-10-21T03:10:00+08:00, cursor: "2026-09" }
```

`cursor` 表示「这一片想到哪了」，中断后从这里接。

## 十、调度：谁会被先想起

分片有限，注意力有限，所以要排序。依据（内核算，纯规则）：

| 因子 | 含义 |
|---|---|
| 距上次整理 | 越久没想，越该想 |
| 近期活跃度 | 最近聊得多的人，记忆变化快 |
| 有未完成 `promise` | 欠着的事优先 |
| 有冲突数据 | 关系值与最近互动明显不符 |

> **这是「谁先被整理」，不是「谁更重要」。**
> 重要性的判断是 DSH 的事，内核只按时间和活跃度排队。

排队的另一面是 08 里的「饥饿」问题：总有人排不上。这属于社交偏好，暂不解决。

## 十一、保护

整理是唯一会大面积改数据的动作。

| 风险 | 防护 |
|---|---|
| 合并出错，丢了细节 | 写入前单文件快照（06 的 4.1） |
| 整理到一半被打断 | 原子替换 + `cursor` 续跑 |
| 一次改了太多，看不出改了什么 | 每次产出**变更摘要** |
| 人格被改坏 | 写入前过基线校验 + 快照（D1） |
| 压缩误删关键信息 | 落盘 → 压缩 → 校验（4.2） |

**变更摘要是给管理员看的**，回答「昨晚它想了什么」。

---

## 十二、自述：整理时说的话，本身也是记忆

整理不是静默的数据处理。角色在独处时会**自言自语**，而这些话被写下来。

| 产物 | 何时 | 长度 |
|---|---|---|
| 短自述 | L0 / L1 | 一两句，进 `memory/core/` |
| 周记 | L2 | ≤ 3000 字，可空 |
| 月报 | L3 | ≤ 3000 字，可空 |

它们共同构成 `memory/journal/`——角色**没有对话对象时说的话**。

### 为什么它重要

如果没有自述，整理就只是数据维护——角色在「后台」不存在，只在「前台」存在。

> **一个只有被呼叫时才存在的东西，不是人。**

### 成本

几乎为零：整理本来就在调模型，自述是那次调用的顺带输出，与体验块同理（05 的第三节）。

---

## 十三、L2 演进提议的唯一出口

维度演进（09 的 L2）不能自动执行，而它的唯一触发点就是**月度整理**。

条件：**发生了现有维度解释不了的事**。

例如反复出现「明明是朋友却要客气」→ 现有 `formality` + `closeness` 解释不了 → 可能需要 `reciprocity`（人情）。

产出不是直接改 schema，而是一条**提议**：

```yaml
proposal:
  action: add_dimension
  key: reciprocity
  reason: "多次出现『不好意思拒绝』的情形，现有维度无法表达"
  evidence: [m_...031, m_...044]
  behaviors:
    高: [不轻易麻烦他, 受了帮助会记着]
```

管理员确认后才生效。

> **L2 慢，不是因为技术慢，而是因为改变「怎么看人」这件事，必须有人点头。**

## 十四、未决

1. **压缩的可控性边界**：落盘后压缩，若模型仍丢掉已落盘的要点，是否要阻止压缩？（倾向：不阻止，落盘已是备份）
2. **周记/月报的归属**：放 `journal/` 独立于 `core/`，两者的边界是否清晰？
3. **归档是否可检索**：索引覆盖归档会变大，是否只索引最近 N 个月？
4. **月度整理的成本**：按人跨月分片，人数多时一个月跑不完怎么办？
5. **变更摘要的粒度**：给管理员看到什么程度？太细是噪音，太粗看不出问题。
6. **周记/月报的字数上限是否统一**：都是 3000 字，但月报的视野更宽，是否该更长？
