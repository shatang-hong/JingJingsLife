## 一、先分清：压缩 ≠ 整理

这两个概念在 11 里被混在一起，必须先拆开。

| | 上下文压缩 | 记忆整理 |
|---|---|---|
| 对象 | 单个 DSH session 的对话上下文 | `character/` 下的文件 |
| 目的 | 腾出窗口 | 合并、归档、演化 |
| 频率 | 高频（每天多次） | 低频（L0 每次闲暇，L3 每月） |
| 期间能否对话 | **不能**（下文） | 能（可中断） |
| 谁触发 | 内核 | 内核 |
| 谁执行 | DSH | DSH |

**T3 / T6 只关于前者。** 11 的 L1 写的「落盘 → 压缩 → 校验」里，前一步是整理，后两步是压缩。

## 二、压缩到底发生在哪（实测修正）

> 本节在 2026-10-23 做过实测，结论与初版设计有重要出入，**以实测为准**。
> 详见 `probes/result.yaml` 的 `P3_compact`。

### 2.1 事实：压缩不在 DSH，在 HTTP 代理层

实际链路：

```
DSH ──→ billion-context 代理（127.0.0.1:18788）──→ 模型 API
                    ↑ 上下文在这里被修剪
```

证据：

| 事实 | 出处 |
|---|---|
| 插件 `billion-context` 监听 18788，夹在 DSH 与上游之间 | 进程列表 |
| 它的 `dsh-compaction-gate.js` 把 DSH 原生的 `dsh-compaction-basic`、`dsh-command-compact` 置为 `disabled: true` | 插件源码 |
| 31 个 DSH settings 命名空间里没有压缩开关 | `settings/describe` |

结论：

> **「关闭 DSH 自动压缩」这件事，这个插件已经替我们做了。**

我们原本担心的「DSH 一边聊一边压」不成立——压缩根本不在 DSH 里。

### 2.2 三个设计变化

| 初版设计 | 实测后 |
|---|---|
| 内核要触发压缩 | **不需要**，代理按阈值自动触发 |
| 内核要知道「DSH 忙不忙」 | **不需要**，压缩在一次请求内部完成 |
| 阈值由内核实现 | 改成**配置代理的参数** |

第二条尤其重要：它意味着 **T6 大概率天然不存在**。压缩发生在「内核 → DSH → 代理 → 模型」这一跳里，DSH 只是等得久一点，不存在「压缩时来消息怎么办」。

> 仍需一次实测确认：发一条会触发压缩的消息，观察 DSH 的响应耗时是否只是变长、而非出现新的状态。

### 2.3 一个新的约束：参数是全局的

代理的阈值是**全局配置**（或按 provider / model 分），不是 per-session。

对单角色无影响——本来就是单注意力。但将来若多个角色共用一台机器上的代理，就必须拆成多个代理实例，否则它们的压缩阈值会互相干扰。

这条要记进 22 的多角色约束里。

## 三、T3：什么时候压

### 3.1 三级触发 → 落到代理参数

`billion-context` 的 `compress.*` 参数**直接支持 token 数**，不需要换算成百分比：

| 我们的级别 | 默认值 | 代理参数 |
|---|---|---|
| 软触发（增长门限） | 100k | `compress.nudgeGrowthTokens` |
| 加速（分级触发） | 110k | `compress.tierNudgeTokens.t2` |
| 硬触发（强制折叠） | 130k | `compress.maxContextLimit` |
| 最近消息保护 | — | `compress.preserveRecentMessages`（默认 3） |

```json
// ~/.config/billion-context/billion-context.json
{
  "compress": {
    "maxContextLimit": 130000,
    "nudgeGrowthTokens": 20000,
    "preserveRecentMessages": 3
  }
}
```

关键点：`maxContextLimit` 的类型是 `number | "N%"`，**可以直接写 `130000`**。这是「用绝对量而非百分比」这条设计能落地的原因。

> ⚠️ 上面的数值是**按实测窗口临时标定的默认值**，不是常量。换 provider 或换模型后必须重算（见 3.5）。

三级的意义：**在「不频繁打断」和「不拖到必须打断」之间留出过渡**。

只有一条线的话，要么太早（频繁打断话题）要么太晚（只能在最不合适的时候打断）。

### 3.2 为什么早早压，明明还有空间

这是最容易被质疑的一点。

因为**压缩的目的不是腾空间，是保持注意力密度**：

| 目的 | 触发点 |
|---|---|
| 装不下才压 | 接近窗口上限（数值运行时读） |
| **保持专注** | **100k–130k** |

对话超过十万 token 后，早先的内容对当前回复的贡献已经很低，但仍然在稀释注意力、推高成本。

> **所以早压不是浪费，是维护质量。**

### 3.3 一个必须接受的让步：没有「断点」概念

代理按 **token 量**触发，不认「空闲时长」。

所以我们原来设计的「等一个自然断点再压」，**做不到**。

代理能提供的近似保护只有一条：

> `compress.preserveRecentMessages: 3` —— 最近 3 条消息不参与折叠。

也就是说：**压缩可能发生在话题中间，但最近几句是安全的。**

这是诚实的让步：

| 想要 | 实际 |
|---|---|
| 只在话题结束时压 | ❌ 做不到 |
| 最近几句一定保得住 | ✅ 有 `preserveRecentMessages` |
| 零实现成本 | ✅ 改配置即可 |

若坚持「只在断点压」，就得在代理前面自己加一层调度，成本远大于收益。

### 3.4 配置在哪、谁改

| 值 | 位置 |
|---|---|
| 三个阈值 | `~/.config/billion-context/billion-context.json` 的 `compress.*` |
| 已用 tokens | `session/projections`（见 5.2），**只用于观测与告警** |
| 窗口上限 | 见 3.5——两处数字不一致 |

注意：**阈值不是角色数据**，所以不放 `character/setting.yaml`——它在角色之外，属于部署配置（见 [25-部署拓扑](25-部署拓扑.md)）。

### 3.5 窗口值必须运行时读，不能写死

实测时两处数字对不上：

| 来源 | 窗口 | 怎么来的 |
|---|---|---|
| DSH 配置 | `1,000,000` | `llm-deepseek.defaultContextWindow` |
| 代理实测 | `268,000` | `/__bili/stats` 的 `contextWindow`，`contextTokensSource: "usage"` |

> ⚠️ **这两个数字都不能作为设计依据。**
> 实测环境用的是桥接模型；生产环境将用专有 API Key 直连，窗口与上报口径都可能不同。

所以真正的结论只有一条：

> **窗口值必须在运行时从 `/__bili/stats` 读，任何地方都不能写死。**

三条派生约束：

| # | 约束 |
|---|---|
| 1 | `maxContextLimit` 用绝对 token 数配置时，该值要随实测窗口标定 |
| 2 | 三个阈值（100k / 110k / 130k）是**默认值，不是常量**——首次部署按实测窗口重算 |
| 3 | 若真实可用窗口远大于 1M，阈值应同比例上调，否则会过早压缩、白白丢细节 |

3.2 节「为什么 130k 就压」的论证方向仍成立（**要留余量**），但具体数值待生产环境标定。

### 3.6 一个好消息：阈值可以热改

实测：直接改写 `~/.config/billion-context/billion-context.json`，3 秒后 `/__bili/config` 就返回了新值，**不需要重启代理，更不需要重启 DSH**。

```bash
curl -s http://127.0.0.1:18788/__bili/config   # 当前生效配置
curl -s http://127.0.0.1:18788/__bili/stats    # 各 session 的用量与窗口
```

对架构的影响：

> **内核可以运行时调整压缩阈值**，不必重启任何东西。

这恢复了初版设计里「内核控制压缩时机」的一部分能力——虽然不能精确到「等断点」，但能到「改阈值」。

注意：`/__bili/config` 返回的是**读到的配置**，是否在下次请求才真正生效，仍需观察（记在 T7 的验证里）。

## 四、T6：压缩期间的消息

> **先读 2.2**：压缩在代理层内部完成，DSH 不产生「忙」状态。
> 所以本节描述的排他机制**大概率不需要实现**——保留原文，作为「万一压缩确实影响了轮次」的预案。

### 4.1 排他，但有上限

```
内核决定压缩
   ↓
标记该 session 为 compacting
   ↓
新消息照常入队，但不投递
   ↓
压缩完成 ──→ 恢复投递
   ↘
   超时（默认 20 秒）──→ 放弃本次压缩，恢复投递
```

### 4.2 为什么超时要放弃

因为**回复用户比清理上下文重要**。

| 选择 | 后果 |
|---|---|
| 一直等压缩 | 用户等了 40 秒没回应，以为掉线 |
| 放弃压缩先回消息 | 上下文更满了，但人还在 |

而且放弃是**安全**的：压缩失败不会损坏数据，只是窗口没腾出来。下一轮再试。

### 4.3 放弃后不要立刻重试

否则会陷入「每轮都试、每轮都超时」的死循环。

规则：**放弃后冷却 N 分钟**（建议 10 分钟）再试，或者等到超过硬触发线。

### 4.4 超时期间 DSH 还在压吗

技术上是的——内核只是不再等待。所以有两种处理：

| 方案 | 说明 |
|---|---|
| **A. 放弃等待，但仍认为它在压** | 后续消息继续排队，直到 DSH 自己回到空闲 |
| B. 放弃等待，认为它已空闲 | 直接投递，可能与压缩并发 |

选 **A**。因为 B 会造成「一边压缩一边对话」，而那正是 2.1 说的注意力失真。

代价：如果 DSH 卡死在压缩里，这个 session 就废了。所以需要第六条。

### 4.5 卡死的兜底

| 检测 | 处理 |
|---|---|
| `compacting` 状态持续 > 5 分钟 | 强制标记为异常，记 trace ERROR |
| 该 session 连续 3 次异常 | 标记为 `degraded`，GUI 告警 |
| `degraded` 后 | 仍可对话，但不再尝试压缩（接受窗口爆掉） |

> **宁可放弃一个 session 的上下文管理，不可让它彻底不出声。**

## 五、接口补充

05 的四个动作里包含 `compact`，这里补它的返回结构，并给 `reply` 加一个字段。

### 5.1 新增 `compact`

| 动作 | 方向 | 语义 |
|---|---|---|
| `compact` | 内核 → DSH | 压缩指定 session 的上下文 |

同步调用，返回：

```yaml
compacted: true | false
tokens_before: 92000
tokens_after:  31000
duration_ms:   8400
error: null            # 失败时的原因
```

### 5.2 上下文用量从哪来

两条路，**均已实测可用**：

| 方式 | 成本 | 说明 |
|---|---|---|
| DSH 在 `reply` 里回报 | 零额外调用 | **首选** |
| `/__bili/stats` | 一次轻量读 | **更早、更细**——压缩发生前就能看到逼近 |
| 内核查 `session/projections` | 一次轻量读 | 兜底；含 `counts.compactions` |

```yaml
context_usage:
  tokens: 74500
  limit:  <从 /__bili/stats 读取>   # 不写死，随 provider 变
```

**为什么首选回报**：每轮主动查就多一次调用；回报是搭车，零成本。

**但 `projections` 有个额外价值**：它同时返回 `counts.compactions`——**压缩次数**。

这是「压缩是否真的发生过」的唯一直接证据，也是 13 的 trace 应当记录的东西。

> 实测（2026-10-23）：`projections` 返回 `contextTimeline.current.{system,tools,user,assistant,total}` 与 `counts.compactions`，字段可用。

## 六、与故障降级的关系

| 场景 | 处理 |
|---|---|
| 压缩时 DSH 挂了 | 同 17 的 F2：入队不处理，恢复后补 |
| 压缩失败（返回 false） | 记 trace，冷却后重试 |
| 已过硬触发线仍压不动 | 接受截断（DSH 自己的行为），记 trace ERROR |

第三条要接受：**有些情况救不回来**。硬撑只会让行为更难预测。

## 七、与其他文档的边界

| 文档 | 关系 |
|---|---|
| 11 的 L1 | 它说的「压缩」就是本文；「落盘」是整理，不是压缩 |
| 17 的 F3 | 模型 API 失败与压缩失败是两回事，不要合并处理 |
| 13 的 trace | 压缩必须记：触发级别（软/加速/硬）、耗时、前/后 token、是否超时 |

trace 那条很重要——**没有它，事后无法判断「为什么它突然记性变差」**。

## 八、未决

1. **三个阈值的校准**：100k / 110k / 130k 与 `idle_minutes=3` 都是初值，需按实际对话长度分布调整。
2. **断点的 60 秒**：群聊与私聊是否该不同？
3. **压缩后的质量检查**：怎么确认「重要的事没被压掉」？现在只能靠落盘兜底。
4. **多次压缩的累积损失**：压三次之后，早期内容还剩多少？没有度量。
5. **P3 探针失败时**：如果无法关闭自动压缩，本文第二、四节作废，需要重新设计。
