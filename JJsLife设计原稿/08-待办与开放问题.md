## 二、开放问题

| # | 议题 | 说明 |
|---|---|---|
| 1 | **饥饿** | 单注意力 + 热聊群 → 另一个群永远排不上。人类是有意识地忽略。所以这里需要的不是调度算法，而是**社交偏好**的表达——它属于人格，不是技术参数。 |
| 2 | **检索上限** | 文件即记忆，规模上去后 grep 失效。需要预留派生索引的位置（07 的索引设计已是兑现，但长期记忆侧还没有）。 |
| 3 | **维度冲突的优先级** | `power: 上位` 与 `closeness: 亲密` 同时成立时（如亲近的长辈），行为集冲突怎么裁决。见 [09](09-人格侧面投影.md) 未决 3。 |
| 4 | **多人管理的 actor 区分** | 一个角色有多个管理员时，审计里如何区分到人。见 [14](14-管理入口.md) 未决。 |
| 5 | **管理员输出格式约束的落实** | 「禁止第一人称」如何保证被执行，而不是被模型软性忽略。见 [14](14-管理入口.md) 未决。 |

## 三、设计缺口盘点

| # | 缺口 | 状态 | 说明 |
|---|---|---|---|
| **G1** | 群作为关系节点 | ✅ 见 [15](15-主体与群.md) | 关系网络只有 person，群没有结构化归宿 |
| **G2** | 多模态（图片 / 表情） | ✅ 见 [16](16-多模态消息.md) | 只处理文本，真实聊天大量是图 |
| **G3** | 知识库 | ✅ 见 [18](18-知识库.md) | 工具面而非注入面；按置信度分流闸门 |
| **G4** | 故障与降级（离线模式） | ✅ 见 [17](17-故障与降级.md) | 渠道与推理解耦；故障只影响本层 |
| **G5** | 冷启动 | ✅ 见 [20](20-冷启动.md) | 默认值来自人格；首次对话明确告知 |
| **G6** | 成本与注入预算 | ✅ 见 [22](22-运行与治理.md) | 三份预算分开；固定开销不随成长膨胀 |
| **G7** | 输出形式 | ✅ 见 [21](21-输出形式.md) | 延迟、分段、长度、标点与语气词 |
| **G8** | 多角色 | ✅ 见 [22](22-运行与治理.md) | 一个角色一个内核实例 |
| **G9** | 角色退役 | ✅ 见 [22](22-运行与治理.md) | 停用 / 封存 / 销毁三态 |
| **G10** | 隐私与数据权利 | 🟡 见 [22](22-运行与治理.md) | 保证所有者可彻底清除；对话者自助删除不做 |
| **G11** | 并发保护 | ✅ 见 [22](22-运行与治理.md) | 租约锁，非文件锁 |
| **G12** | 群成员数据的获取 | ✅ 见 [15](15-主体与群.md) 8.9 | 只对发言者建模，不依赖渠道成员列表 |
| **G13** | 表情库的来源与维护 | ✅ 见 [16](16-多模态消息.md) 6.2 | 自动收藏 + 人工审批，新收藏不等于可用 |

**优先级建议**：G4（关系到核心判据）→ G3（独立可做）→ G5 / G6（影响日常运行）→ 其余按需。

## 四、与现有项目的关系

| 项目 | 在新架构中的角色 | 可复用部分 |
|---|---|---|
| qq-bridge | QQ 适配器 | 安全审计、SSRF 防护、MCP 进程隔离、不可变基线校验、Token 记账 |
| WeChatAgent | 参考实现（已有渠道抽象） | `adapters/` 渠道接口、Session 映射、Reply Protocol、上下文压缩 |

**阶段 1 的正确入口**：不是去解剖 qq-bridge 的万行 `bridge.js`，而是在 WeChatAgent 的 adapter 接口上补贴一层内核 API。

qq-bridge 的价值在横切的安全模块，可直接搬。
