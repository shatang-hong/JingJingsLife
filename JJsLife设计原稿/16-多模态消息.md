# 16 · 多模态消息

> 上游：[03-实时记忆](03-实时记忆.md)｜ [10-长期记忆条目](10-长期记忆条目.md)｜ [15-主体与群](15-主体与群.md)

## 一、问题

真实聊天大量是非文字：图片、表情包、语音、链接卡片、引用回复、合并转发。现有设计只有 `text`：收到图只看到「[图片]」，表情包无处可发（09 的行为集没有这一项），记忆无法记「他发过一张猫的照片」。WeChatAgent 已支持这些能力，但数据结构没留位置。

## 二、消息对象加 `media`

消息对象加一个 `media` 数组，元素含 `kind`、`ref`、`size`、`meta`。

| 字段 | 作用 |
|---|---|
| `kind` | 处理方式：图片走视觉模型，表情查库，链接抓正文；取值 image / sticker / voice / video / file / link |
| `ref` | 内容 hash：去重、可引用、日志不泄露内容 |
| `size` / `meta` | 排查用（如 `{ w: 800, h: 600 }`），可替代原文进日志 |

不为每种类型建字段，差异放 `kind` + `meta`。

## 三、内容寻址存储

媒体存 `character/media/<hash 前2位>/<hash>.<ext>`。

| 好处 | 说明 |
|---|---|
| 天然去重 | 同一张图转发十次只存一份 |
| 可引用 | 消息、记忆、日志引用同一个 `ref` |
| 日志安全 | 日志只出现 hash（13 的占位符规则直接复用） |

## 四、关键判断：记忆存描述，不存原始文件

存原始文件会无限膨胀且像素对角色无意义；只存描述则失去「再看一眼」的能力。

**答案：两者都要，但寿命不同。**

| 对象 | 寿命 |
|---|---|
| **原始媒体** | 短期（默认 30 天，可配），过期即删 |
| **文字描述** | 永久，写在记忆条目里 |

条目形态：`type: event`，`people` 记当事人，`media` 记 `{ kind: image, ref: "sha256:9f2a…", expired: true }`，正文是描述文字——记忆本就是描述而非原始数据，媒体存储因此不会无限增长。描述由 DSH 看图时顺手写一句，是该次调用的顺带产物，零额外成本（同 05 第三节体验块）；过期后 `ref` 文件已删，条目标 `expired: true`。

## 五、语音

PoC 不做，数据模型留位：`kind: voice` + `meta: { duration: 12 }`，描述由 DSH 写。

| 方向 | 需要什么 |
|---|---|
| 入站 | ASR 转文字，或直接把音频给多模态模型 |
| 出站 | TTS |

## 六、出站：角色怎么「说」

09 的行为集管**内容约束**（能不能提私事），不管**形式**；这里补形式。

### 6.1 输出协议扩展

沿用 Reply Protocol，只有四种标记：`RESPOND: 文字`（纯文本）、`RESPOND: [STICKER:S3] 文字`（先表情后文字）、`RESPOND: [IMG:sha256:…] 文字`（发已有媒体）、`SILENCE`。

### 6.2 表情库：候选与可用分离

目录 `character/assets/stickers/` 分 `candidates/`（自动收藏）、`approved/`（管理员批准）、`index.yaml`（只索引 approved）。

| 状态 | 能否使用 | 谁决定 |
|---|---|---|
| 候选 | ❌ | 角色收藏 |
| 已批准 | ✅ | 管理员 |

**新收藏 ≠ 直接能用。** 表情是对外表达，一张不合适的表情会毁人设，且**发出去收不回来**。

### 6.2.1 实现策略：能力用 `dsh-meme`，闸门自研

**结论：检索、分类、发送推荐用 `dsh-meme`；「候选 → 可用」审批自研。** 判据见 [refs/installed-plugins](refs/installed-plugins.md)：**载体自研，工具可推荐。**

| 能力 | 我们的原设计 | `dsh-meme` |
|---|---|---|
| 检索 | 首轮注入 `id + 极短描述`（约 120 字固定开销） | 工具面：`send_meme` 按情绪 / 关键词搜，候选带 `caption` |
| 分类 | 自建 `emotion` / `tags` | 6 个情绪桶 + caption / 关键词 / 图名子串搜 |
| 出站 | Reply Protocol `[STICKER:S1]` | 文字标记 → 前端 / IM 显示图片，与 [21](21-输出形式.md) 同构 |

`caption` 让模型自己判断「贴不贴」，判断权在 DSH，符合 I3；也与 [18-知识库](18-知识库.md) 的**工具面而非注入面**一致。

### 6.2.2 三个必须处理的差异

**差异一：存储位置可配。** `memeRoot`、`packsDir` 可配，优先级 用户设置 > patch 配置 `config.memeRoot` > 插件包内默认；在 `cordis.patch.yml` 指定 `config.memeRoot: <角色目录>/assets/stickers`，**角色包就能带走表情库**，符合 [06](06-角色数据契约.md) 迁移要求。

**差异二：没有逐张审批闸门。** 它只有图库级 `enabled`。**✅ 采用批次审批**：新图先进**独立图库**（`enabled: false`），管理员整批验收后启用——粒度粗但够用；真实风险是风格不符人设，逐张审批不可持续。

| 落地规则 | 说明 |
|---|---|
| 新图落 `pending-<日期>/` | 对应一个 `enabled: false` 的图库 |
| 深整理生成候选清单 | 本批图 + caption + 建议场景 |
| 管理员整批启用或整批弃用 | 不做单张裁决 |
| 已启用的图**不单独撤下** | 撤就撤整个图库，避免风格混杂 |

**差异三：图库市场加约束。** **只允许管理员手动安装，装完默认 `enabled: false`**，验收后启用。

### 6.2.3 审批挂在深整理上

每周深整理（L2）时，DSH 把本周新收藏的表情列成候选清单，每条附 `desc`、来源会话、建议使用场景；管理员在 GUI 里逐条批准或忽略——批量、可视化、可撤销（14 的第二节）。

### 6.2.2 与「维度提议」是同一个机制

| 产物 | 谁提议 | 谁批准 |
|---|---|---|
| 新维度（09 的 L2） | DSH | 管理员 |
| 新表情 | DSH 收集 | 管理员 |
| 新黑话 | DSH 提取（qq-bridge 模式） | 管理员 |

共用一条：**自动学习产生候选，人工闸门决定生效。** 详见 09 的 8.4。

### 6.3 发不发：两层决定

| 层 | 决定什么 | 依据 | 解决 |
|---|---|---|---|
| **许可** | 能不能发 | `approved` 白名单 + 场合 | 会不会出事 |
| **倾向** | 多常发 | 关系档位 | 像不像人 |

| 许可：场合 | 允许 |
|---|---|
| `formality: 正式` | ❌ |
| `formality: 随意` | ✅ |
| `safety: 谨慎`（群） | ❌ |
| `safety: 放松`（群） | ✅ |

| 倾向：表情密度 | 条件 | 表现 |
|---|---|---|
| 无 | `formality` 正式 / `safety` 谨慎 | 纯文字 |
| 低 | `closeness` 低 | 偶尔 |
| 中 | `closeness` 中 | 有时 |
| 高 | `closeness` 高 + `formality` 随意 | 经常 |

落地：不新增维度，走行为集。`sticker_density` 是 (closeness, formality, safety) 的行为集产物——`_schema.yaml` 里「亲近」带「可主动开启话题 + `sticker_density: 中`」，「亲密」带「可询问私人近况 + `sticker_density: 高`」。

## 七、日志

沿用 13 的占位符规则，日志写 `<media kind=image sha256:9f2a size=102400>`——内容寻址本身即占位符。

## 八、PoC 范围

| 能力 | PoC | 说明 |
|---|---|---|
| 图片入站 + 描述 | ✅ | 微信最常见 |
| 表情出站 | ✅ | 成本低，效果明显 |
| 图片出站 | ⭕ 可选 | 复用已收图 |
| 语音 | ❌ | 需要 ASR / TTS |
| 视频 | ❌ | 同上 |
| 文件 | ❌ | 只记文件名 |

## 九、未决

1. **媒体保留期**：30 天是否合适？被反复引用的图是否应延长？
2. **描述的质量**：DSH 写的描述可能过简或过详，是否需要约束？
3. **表情库的来源**：人工整理？还是从聊天自动收集（WeChatAgent 有 `learn_meme`）？
4. **图片出站的场景**：什么情况下应发图而不是描述？
5. **引用回复与合并转发**：WeChatAgent 做了，`media` 结构是否够用？还是需要单独的 `quoted` 字段？
