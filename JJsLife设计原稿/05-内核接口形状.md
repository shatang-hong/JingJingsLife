## 一、三个时间尺度

| 尺度 | 定义 | 归属 | 对应动作 |
|---|---|---|---|
| **episode**（片段） | 一次注意力占用：进入某会话 → 离开 | 内核 | 注意力交接 |
| **turn**（轮） | 一次推理：一批新消息 → 一次回复 | DSH | deliver / reply |
| **idle**（闲暇） | 注意力为空 | 内核 | 整理 |

层级：

```
episode     一次进入某会话到离开
  └─ turn       一轮消息 → 一次 DSH 调用
       └─ 产出：回复 + 事实便签（可选）+ 体验块（可选）
```

### 边界结论

**片段 ≠ 一轮。**

- 片段是**注意力单位**
- 轮是**推理单位**

挂载关系：

- 写入挂在**轮**上
- 归档挂在**片段结束 + 闲暇**

这个区分之前一直模糊，是因为把「注意力单位」和「推理单位」压在同一个词里。

## 二、交接时交出去什么

### 2.1 内核 → DSH（每轮，只推增量）

| 项 | 说明 |
|---|---|
| 新消息 | 本批未处理的消息，不多不少 |
| 时钟 | 绝对时间、距上次联系、本段已持续、被打断次数、闲暇时长 |
| 实时记忆 · 事实视图 | 最近 N 条未过期便签，**剔除 `from_session == 当前会话`** |
| 实时记忆 · 在场视图 | 最新一条体验块（**不含自己的**） |

### 2.2 DSH → 内核（每轮）

| 项 | 必需 |
|---|---|
| 回复（RESPOND / SILENCE / 表情标记） | 是 |
| **上下文用量（`tokens` / `limit`）** | 是（见 27） |
| 事实便签 | 否 |
| 体验块 | 否（内核保留最新一条） |

### 2.3 关键：内核不推送历史

session 上下文由 DSH 自己持有。

内核只在**首次进入**时 bootstrap 一次（人格 + 安全基线 + 该会话的初始记忆），之后只推增量。

否则每轮重推历史会同时踩两个雷：

1. 成本爆炸
2. 与 session 里的既有上下文重复

## 三、体验块什么时候生成

**不作为独立调用**，附在每轮输出里，内核保留最新一条。

理由：

- 单独安排一次「收尾调用」成本翻倍
- 人也不是专门花时间「生成记忆」，是聊着聊着就记住了
- 与事实便签共用同一输出通道，零新增机制

**兜底**：若某轮未给体验块，内核用「最后一条消息 + 时间」做机械兜底，不追求完整。

## 四、空闲动作

### 4.1 触发

注意力队列为空 + 当前会话静默超过阈值（见 04 的 D5）。

### 4.2 执行者：整理会话

一个**独立的 maintenance session**，不是任何联系人会话。

理由：整理需要读取全部记忆文件的全局视角。联系人会话的上下文里全是那个人的事，不适合做全局整理。

| 特征 | 要求 |
|---|---|
| 身份 | 无联系人身份（「角色独处时」） |
| 工具面 | 记忆文件读写 |
| 上下文 | 独立，可较长 |
| **可中断** | 中途来消息 → 立即让位 |
| **可续** | 未完成的整理进度不丢 |

### 4.3 为什么「可中断」最重要

否则角色会因为「正在回想」而不理人——这不像人。

一个能被消息打断的整理，也意味着整理必须是**分片可续**的，不能是「一口气写完」的事务。

> 注意：这里说的「被打断」指**整理会话**。**上下文压缩**不是整理——它排他、不可中断、且必须由内核触发，见 [27-上下文压缩](27-上下文压缩.md)。

## 五、四个动作 + 一组工具面

| 动作 | 方向 | 语义 |
|---|---|---|
| `deliver` | 内核 → DSH | 投递一轮：新消息 + 时钟 + 实时记忆视图 |
| `reply` | DSH → 内核 | 回复 + 可选便签 + 可选体验块 + **上下文用量** |
| `idle` | 内核 → DSH | 唤起整理（可中断、可续） |
| `compact` | 内核 → DSH | 压缩该 session 的上下文（排他、有超时，见 27） |

**实测修正（2026-10-23）**：DSH 的投递是**异步**的——`session/prompt` 只返回 `{ accepted: true }`，回复必须另取。

所以「一次同步往返」不成立。实际是两段：

| 阶段 | 动作 |
|---|---|
| 投递 | `session/prompt { requestId, sessionId, mode, content }` → `accepted` |
| 取回 | 从事件流取，或读会话记录（等到 `turn/end`） |

对内核的影响：**`deliver` 不能假设「返回即拿到回复」**，必须有一个「等待本轮结束」的机制。

### 取回的两条路

| 方式 | 可行性 | 用于 |
|---|---|---|
| 轮询会话文件（`session.v4.jsonl.zstd`，多帧 zstd） | ✅ 已验证 | **PoC** |
| `/stream` 流载体 + `session/follow` | ⚠️ 协议未查明（POST 405 / GET 404） | V1 |

**PoC 用文件轮询**：500ms–1s 间隔，读到 `turn/end` 即本轮结束。

代价是每轮都要解压整个文件，随会话增长而变慢；但 PoC 会话不长，可以接受。

> `/stream` 是性能优化，不是可行性前提——不要因为它卡住 PoC。

两个现成的好东西：

| 机制 | 含义 | 对应设计 |
|---|---|---|
| `requestId` | 客户端铸造、持久化在用户消息上 | **幂等键**——重投不会产生两条消息 |
| `mode: queue / steer` | 排队 / 插话 | [26](26-社交默认值.md) 的「打断与接续」 |

> **`steer` 是白送的。** 我们原以为要自己做「打断」，DSH 已经把这个能力做在协议里了。

### 5.1 工具面不是动作

`memory.*`、`knowledge.search` 这类不属于上面的动作，它们是 DSH 在推理过程中**自己调用**的工具（MCP），方向同样是 DSH → 内核：

| 工具面 | 挂载者 | 详见 |
|---|---|---|
| `memory.*` | kernel-role | 10 |
| `knowledge.*` | kernel-role | 18 |
| `channel.send` | kernel-role | 16 |

与上面四个动作的区别：

| | 谁发起 | 时机 |
|---|---|---|
| `deliver` / `reply` | **内核** | 一轮的边界 |
| 工具调用 | **DSH** | 一轮之内 |

> 前者决定「什么时候想」，后者决定「想的时候能查什么」。

## 六、一条判据

> **凡是「内核需要理解内容才能决定」的，都不该出现在接口上。**

接口上只允许出现：时间、来源、路径、配额、模式匹配结果。

一旦某个字段需要问「这句话什么意思」，说明职责放错了层。

这条判据在以后每次改接口时都能用。
