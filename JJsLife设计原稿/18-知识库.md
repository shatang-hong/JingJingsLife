## 一、边界：知识不是记忆

三层载体的分工（10 的第一节）在这里要落到一个具体判据上：

| 判据 | 归到 |
|---|---|
| 绑定具体的人 | `relations/` 或 `memory/people/` |
| 绑定具体的场合 | `relations/`（群）或 `memory/groups/` |
| **不绑定任何具体的人或场合** | **`knowledge/`** |
| 关于角色自己 | `memory/core/` |

例子：

| 内容 | 归属 | 理由 |
|---|---|---|
| 小明喜欢猫 | 记忆 | 绑定了小明 |
| 猫喜欢晒太阳 | **知识** | 谁都能用 |
| 这个群不爱长文 | 关系（群） | 绑定了群 |
| Python 协程比线程轻 | **知识** | 不绑定 |
| 我说话别太长 | 人格 | 关于自己 |

一句话：

> **能对所有人说的，是知识；只能对这个人说的，是记忆。**

## 二、关键判断：知识是「工具面」，不是「注入面」

这是本节最重要的设计，它决定了整个接口形态。

### 2.1 记忆与知识的注入方式不同

| | 记忆 | 知识 |
|---|---|---|
| 谁决定用哪个 | **内核**（按节点、时间、类型） | **DSH**（按当前话题） |
| 注入时机 | 每轮预注入 | **按需检索** |
| 原因 | 需要连续性，不知道会漏 | 量大，且内核不知道哪些相关 |

核心原因：

> **内核不知道「这条消息需要什么知识」。** 那是语义判断，违反 I3。

所以知识库不是一个「往里塞内容」的东西，而是一个**提供给 DSH 的工具**：

```
knowledge.search(query) → [ { id, title, snippet, source, updated_at } ]
```

DSH 自己决定要不要查、查什么、用不用。

### 2.2 这个选择的好处

| 好处 | 说明 |
|---|---|
| 成本可控 | 不相关时零成本，不会每轮都塞一堆知识 |
| 符合 I3 | 内核只做 grep 与索引过滤，不做语义判断 |
| 知识可无限增长 | 不进 prompt，只进工具 |

## 三、条目格式

`knowledge/notes/<topic>.md`，一个主题一个文件，内含多条。

````markdown
### k_20261023_001

```yaml
title: Python 协程与线程的开销差异
tags: [python, 并发]
source: https://example.com/article
confidence: 0.9
ttl: null                  # 永不过期
updated_at: 2026-10-23
status: active             # active | superseded | expired
```

协程的切换在用户态完成，不涉及内核调度；线程切换需要陷入内核。
所以 IO 密集场景下协程的内存与切换开销都更低。
````

| 字段 | 作用 |
|---|---|
| `source` | 可追溯。**没有来源的知识不该存在** |
| `confidence` | 决定是否需要人工确认 |
| `ttl` | 时效性。新闻类必须设，常识类可为 null |
| `status` | 过期不删，标 `expired`（与记忆一致） |

## 四、来源与置信度

| 来源 | `source` 形态 | 初始 `confidence` | 闸门 |
|---|---|---|---|
| 管理员上传 | `admin:<file>` | 1.0 | 直接入库 |
| 对话中用户明确告知 | `dialogue:<memo_id>` | 0.8 | 直接入库 |
| DSH 联网检索 | URL | 0.6 | 直接入库，低优先级 |
| DSH 从对话推断 | `dialogue:<memo_id>` + `inferred` | 0.4 | **进候选队列** |

### 4.1 闸门分层（不是全都要人批）

09 的 8.4 说「自动学习的产物都要过闸门」，但知识量太大，全批不现实。

所以按**置信度**分流：

```
confidence ≥ 0.7  → 直接入库
confidence <  0.7  → candidates/，等管理员批
```

这条由**内核**执行（纯阈值比较），不需要判断内容。

### 4.2 为什么可以放宽

因为知识不像表情——**说错了可以纠正**。

| 产物 | 错了的后果 | 闸门 |
|---|---|---|
| 表情 | 发出去收不回来 | 严（逐条批） |
| 知识 | 被引用后可以更正、可以标 superseded | 宽（按置信度） |

> **闸门的严格程度，取决于错误的可挽回性。**

## 五、时效性

有些知识会过期，有些不会：

| 类型 | `ttl` | 例 |
|---|---|---|
| 常识 | `null` | 猫喜欢晒太阳 |
| 技术 | `null` 或很长 | 协程的开销 |
| 新闻 / 事件 | 90 天 | 「某公司昨天发布了 X」 |
| 人物状态 | 180 天 | 「小明现在在杭州工作」→ 其实这是记忆 |

过期后：

- 标 `status: expired`
- 检索默认不返回，除非显式要求
- **不删除**——过期本身就是信息（「这条可能不准了」）

## 六、冲突：不自动裁决

原构想说「新旧冲突时标记待确认，而不是直接覆盖」。

这里更彻底：**不做自动冲突检测**。

理由：判断两条知识是否冲突，是语义判断，只有 DSH 能做。

所以：

| 层 | 做什么 |
|---|---|
| 内核 | 只按 tag / 关键词返回多条，按 `updated_at` 排序 |
| DSH | 自己看多条，判断哪个更可信、要不要追问 |
| 管理员 | 可手动标 `superseded` 指向新的那条 |

> **内核提供全部候选，让有判断力的一方去判断。**

## 七、目录

```
knowledge/
├── sources/                 # 管理员上传的原始文档
│   └── <name>.md
├── notes/                   # 沉淀笔记，按主题聚合
│   ├── python.md
│   └── 养猫.md
├── candidates/              # 低置信度，待批准
│   └── <id>.md
└── _index.json              # 派生索引：tag / source / updated_at
```

**为什么 `sources/` 和 `notes/` 分开**：

| | 是什么 | 谁写 |
|---|---|---|
| `sources/` | 原文，不改 | 管理员上传 |
| `notes/` | 沉淀后的结论 | DSH 整理时写 |

保留原文的价值：**将来对结论有疑问，可以回到原文核对。**

## 八、整理时对知识做什么

知识也需要整理，但动作和记忆不同：

| 对象 | 动作 |
|---|---|
| 记忆 | 合并、标记废弃 |
| **知识** | **去重、合并同主题、更新 `updated_at`、过期标记** |

具体：

1. 同一主题的多条，合并进同一个 `notes/<topic>.md`
2. 重复结论去重（DSH 判断，因为它要做语义比较）
3. `ttl` 到期的标 `expired`
4. 引用了已过期知识的记忆，不做处理——**记忆是当时的真实**

### 8.1 一个特别的整理动作：来源校验

如果知识来自 URL，整理时可以选择性复核（重新抓一次）。

但成本高，建议只在 `confidence < 0.7` 或 `ttl` 即将到期时做。

## 九、自学

原构想有「AI 自学 → web_search → 提取 → 入库」。

这是很「人」的行为，但要加两个约束：

| 约束 | 理由 |
|---|---|
| 必须留 `source` | 无来源的知识不可追溯，也无法校验 |
| 必须记 `confidence` | 检索到的内容质量参差 |

而且自学的知识**默认置信度低**（0.6），因为：

> 搜到的 ≠ 真的。

真正高置信度的知识应该来自：管理员上传，或用户的明确告知。

## 十一、检索的实现上限

| 规模 | 方案 |
|---|---|
| < 500 条 | 文件名 + grep |
| 500–5000 | 索引按 tag 预筛，再 grep |
| > 5000 | 必须向量检索 |

留位方式：`_index.json` 已按多路设计（tag / source / 时间），将来加一路 `by_embedding` 即可，真源不变。

## 十二、未决

1. **`notes/` 的粒度**：一个主题多大算一个主题？「python」和「python 并发」要不要分开？
2. **置信度阈值 0.7**：能否校准？现在纯经验。
3. **知识的删除权**：管理员上传的文档，被角色引用后能否撤回？（「我教过它，现在不想让它知道了」）
4. **知识的来源引用**：检索结果里要不要带原文片段，还是只给路径让 DSH 再读？
5. **多模态知识**：图片、PDF 进知识库怎么处理？（PoC 只做文本）
