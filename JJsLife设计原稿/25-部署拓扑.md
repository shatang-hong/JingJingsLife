## 一、进程清单

| 进程 | 归属 | 谁启动 | 有状态吗 |
|---|---|---|---|
| **内核** | 本项目 | 用户 | ✅ 持有租约、注意力队列 |
| **QQ 适配器** | 本项目 | 用户 | ⚠️ 只有连接状态 |
| **DSH** | 外部 | 用户 | ✅ 持有 session |
| **SnowLuma** | 外部 | 用户 | ⚠️ 网关连接 |
| **QQ 客户端** | 外部 | 用户 | — |

**GUI 不是一个独立进程**——由内核直接提供静态文件，省一个端口和一份部署负担。

## 三、端口约定

| 服务 | 默认端口 | 环境变量 |
|---|---|---|
| 内核 API + GUI | `7300` | `CHARA_KERNEL_PORT` |
| QQ 适配器 | `7301` | `CHARA_ADAPTER_PORT` |

规则：

- **全部绑定 `127.0.0.1`**，不对外暴露
- 端口冲突时由环境变量覆盖，不用配置文件（配置项越少越好）
- 段位选 7300 是为了避开常见开发端口（3000/5173/8080）与已有项目的 3100/11230

## 四、启动顺序

```
1. DSH（用户常驻）
2. 内核         ← 拿租约、建索引
3. QQ 适配器    ← 拉能力、连 SnowLuma
4. SnowLuma → QQ 客户端
```

**关键：内核必须早于适配器。**

否则适配器连不上，会进入重试。虽然不会崩（17 的 F1），但日志会很难看。

反过来，**适配器晚起是安全的**：渠道断线期间角色照常整理（17 的第三节），这正是第一判据要的效果。

## 五、目录

```
project/
├── character/              # ← DSH 的 cwd（sandbox: workspace-write）
│   ├── identity/           #   L0/L1/L2 三层身份
│   ├── memory/             #   长期记忆 + 归档 + 自述
│   ├── relations/          #   节点 + 边 + schema
│   ├── knowledge/
│   ├── media/              #   短期媒体（不导出）
│   ├── assets/stickers/    #   表情库（导出）
│   ├── runtime/            #   实时记忆、时钟、队列（不导出）
│   └── sessions/           #   DSH session 映射
│
├── ops/                    # ← 工作区之外：DSH 只读、不可写
│   ├── audit/              #   安全审计（长期，不记原文）
│   ├── logs/trace/         #   链路追踪（滚动）
│   └── snapshot/           #   快照
│
└── workspace-admin/        # 管理员 DSH 独享
    ├── migrations/
    ├── diagnostics/
    └── tmp/
```

### 5.1 一条硬约束：DSH 的 cwd 必须是 `character/`

因为 DSH 的沙箱是 `workspace-write`——**工作区内可读可写，工作区外只读**。

所以：

> `ops/` 必须与 `character/` **平级**，不能放在它里面。

一旦 `ops/` 落进工作区，DSH 就能改审计、删快照，前面所有写保护全部失效。

反过来，`character/` 里的东西它都能改——这是有意的：**记忆、人格、关系本来就该由它维护。**

### 5.2 于是「安全感」的来源很清晰

| 想保护 | 手段 |
|---|---|
| 审计不被篡改 | 放在工作区外（DSH 写不了） |
| 快照可回滚 | 同上 |
| 基线不被改 | 同上 |
| 审计不被读取 | ❌ 做不到，所以**不记原文** |

详见 06 的目录布局与 14 的工作区隔离。

## 六、内核持有什么运行时状态

只有三样，且全部可重建：

| 状态 | 落地 | 丢失后果 |
|---|---|---|
| 注意力队列 | `runtime/queue.json` | 丢掉未处理消息（会记一条「忙不过来」） |
| 实时记忆 | `runtime/realtime.log` | 丢最近几轮，长期记忆不受影响 |
| 租约 | `runtime/lease.json` | 重启时被另一个实例抢占（见 22 的第五节） |

**索引不在此列**——索引可随时从真源重建，不属于必须持久化的状态。

## 七、单机假设与它的代价

本设计假设**一台机器、一个人用、一个角色**。

| 假设 | 打破时的代价 |
|---|---|
| 单机 | 需要跨机同步 `character/`，租约机制失效 |
| 单用户 | 需要 actor 区分到人（08 的开放问题 4） |
| 单角色 | 见 22 的第二节，必须多进程 |

> **架构阶段先接受这些假设。** 一旦真的要上多机，需要重新设计的是租约与索引同步，不是角色语义——因为角色语义本来就不依赖机器数量。

## 八、未决

1. **DSH 的启动依赖**：内核启动时 DSH 没起，应该拒绝启动还是降级等待？
2. **GUI 的静态文件从哪来**：内核内置一个极简页面，还是单独构建产物？
3. **Windows 的路径与权限**：D4 的「权限分区」在 Windows 上怎么实现（ACL）？
4. **日志轮转的落地**：13 说按天滚动、保留 7 天，谁来删（内核定时任务）？
5. **多网卡与容器**：将来若要容器化，`127.0.0.1` 的绑定假设会失效。
