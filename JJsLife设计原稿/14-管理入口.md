# 14 · 管理入口

## 一、两个入口，主次分明

| 入口 | 定位 | 使用频率 |
|---|---|---|
| **GUI** | 常规使用：维护参数、填入配置、浏览状态 | 日常 |
| **管理员 DSH 会话** | 兜底：版本更新、GUI 解决不了的问题 | 偶发 |

**GUI 是主界面，DSH 是助手。** 不是反过来。

---

## 二、分工判据：已知 vs 未知

| | GUI | 管理员 DSH |
|---|---|---|
| 擅长 | **已经知道要做什么**，只是要做得快 | **还不知道该做什么**，需要边查边想 |
| 操作形态 | 表单、表格、开关、列表 | 自然语言 + 工具调用 |
| 典型场景 | 改阈值、填账号、认领身份 | 「这周这个群为什么没人理它」 |
| 失败模式 | 遇到没设计过的操作，只能报错 | 遇到需要精确批量操作时，容易出错 |

一句话：

> **GUI 处理「已知的问题」，DSH 处理「未知的问题」。**

所以不能因为有了 DSH 就砍掉 GUI——日常维护是已知问题，用对话做反而慢。

---

## 三、GUI 的职责

| 页面 | 内容 |
|---|---|
| 状态总览 | 内核状态、注意力、队列、渠道连接、最近异常 |
| 配置 | 渠道账号、白名单、模型参数、阈值 |
| 人格 | `persona.md` 编辑、快照列表、回滚 |
| 维度 | `_schema.yaml` 可视化编辑、档位与行为映射 |
| 关系 | 人物列表、关系值、认领 / 合并 / 拆分 |
| 记忆 | 按人/主题浏览、按时间线浏览、标记废弃 |
| 整理 | 各级整理的手动触发、变更摘要、进度 |
| 日志 | trace 查询、审计记录（区分 actor） |
| 导出 | 打包、导入校验 |

写操作全部走内核 API。

---

## 四、管理员 DSH 的职责

它不是日常入口，只在三种情况下上场：

| 场景 | 为什么 GUI 不行 |
|---|---|
| **版本升级 / 格式迁移** | 迁移逻辑没写进 GUI，需要临场判断 |
| **复杂诊断** | 「为什么它对这个人的态度突然变了」——要跨日志、记忆、关系联合分析 |
| **一次性批量操作** | 只做一次的事，不值得为它做界面 |
| **schema 演进评估** | 判断「现有维度是否解释不了」，需要读大量记忆做归纳 |

它的优势是**开放式**，代价是**不可复现**。

所以：凡是 DSH 做过一次、以后还会再做的事，都应该沉淀成 GUI 操作或脚本。

> **DSH 是接生婆，不是常驻保姆。**

## 五、工作区隔离

三个进程，三个工作区，边界必须清楚。

| 进程 | 工作区 | 对 `character/` 的权限 |
|---|---|---|
| **角色 DSH** | `character/` 本身就是它的 workdir | 读写（受 D4 分区限制） |
| **管理员 DSH** | `workspace-admin/`（独立） | **只读** |
| **GUI / 内核 API** | 无独立 workdir | 读写（经内核 API） |

```
project/
├── character/            # 角色数据。角色可读写；管理员只读
├── workspace-admin/      # 管理员 DSH 独享。角色进程不可见
│   ├── migrations/       # 迁移脚本
│   ├── diagnostics/      # 诊断笔记
│   └── tmp/              # 临时分析
└── ...
```

### 5.1 为什么管理员要独立工作区

三个理由：

1. **不污染角色目录**。迁移脚本、临时分析文件若落在 `character/` 内，会被打包带走、会被算进"角色本体"。
2. **角色进程不可见**。角色不该知道"有人在研究它"。
3. **可整体清理**。诊断完可以整个删掉，不影响角色。

### 5.2 单向读取

| 方向 | 允许 |
|---|---|
| 管理员 DSH → 读 `character/` | ✅ |
| 管理员 DSH → 写 `character/` | ❌ **只能经内核 API** |
| 角色 DSH → 读 `workspace-admin/` | ❌ 不可见 |
| 角色 DSH → 读 `character/` 之外 | ❌ |

第二条很关键：管理员 DSH **不能直接改文件**，即使它在物理上有能力。

因为它一旦直接改文件，就绕过了快照、审计、基线校验。

> **只读文件系统，写必须走 API。**

## 六、三个入口，一个写入口

```
GUI ─────────┐
             │
管理员 DSH ──┼──→ 内核 API ──→ character/
             │
角色 DSH ────┘（仅 memory.* / channel.send）
```

所有写操作收敛到内核 API 一处。好处：

| 保证 | 说明 |
|---|---|
| 审计只有一处 | `actor` 字段区分来源 |
| 快照不会漏 | 不经 API 的写，一律没有快照 |
| 基线校验不会漏 | 同上 |
| 权限只有一套 | 不用在三个地方各写一遍 |

### 6.1 `actor` 的取值

| 值 | 来源 |
|---|---|
| `role` | 角色自己的行为（记忆、关系、人格演化） |
| `admin:dsh` | 管理员会话经 API 的操作 |
| `admin:gui` | GUI 经 API 的操作 |
| `system` | 内核自身（索引重建、按时触发整理） |

审计里能一眼看出「这条是谁干的」，这是 08 里「多人管理」问题的基础。

## 七、三层身份

| 身份 | 是什么 | 读什么 |
|---|---|---|
| **角色** | DSH 扮演的人 | 自己的记忆与人格 |
| **管理员** | 人（经 GUI 或 DSH） | 角色数据、配置、日志 |
| **渠道** | 适配器 | 只有协议字段 |

> **角色有「感受」，管理员只有「视图」。**

### 7.1 管理员会话不占角色注意力

I2 说「注意力只有一个」。那管理员 DSH 也在推理，是否违反？

不违反。I2 约束的是**角色**的注意力：

| 谁在思考 | 受 I2 约束吗 |
|---|---|
| 角色会话 | ✅ 严格单注意力 |
| 管理员会话 | ❌ 它不是角色，是管理员在操作工具 |

角色仍然一次只想一件事。管理员在另一个窗口查日志，不会让角色变成「同时想两件事」。

## 八、工具面物理隔离

沿用 qq-bridge 的 MCP 隔离模式。

| MCP Server | 谁挂载 | 提供什么 |
|---|---|---|
| `kernel-role` | 角色会话 | `memory.*`、`channel.send` |
| `kernel-admin` | 管理员会话 | `status`、`trace`、`relations.*`、`schema.*`、`claim`、`maintenance`、`export`、`rollback` |

角色会话**物理上访问不到** admin 工具。不是「没权限」，是「没这个工具」。

### admin 工具清单（初版）

| 工具 | 作用 | 写 |
|---|---|---|
| `status` | 内核状态、注意力、队列、健康 | 否 |
| `trace.query` | 查链路日志 | 否 |
| `memory.list` | 列条目元数据（不含正文） | 否 |
| `memory.read` | 读某条正文 | 否，但**留痕** |
| `relations.get` | 查关系与档位 | 否 |
| `relations.set` | 改关系值 / 档位 | 是 |
| `schema.get` | 读维度定义 | 否 |
| `schema.propose` | 提交变更提议 | 否 |
| `schema.apply` | 应用变更 | 是，需二次确认 |
| `claim` | 认领渠道身份 | 是 |
| `maintenance.run` | 手动触发某级整理 | 是 |
| `export` | 打包角色 | 否 |
| `rollback` | 回滚到快照 | 是 |

## 九、管理员 DSH 的七条约束

### 1. 不注入人设

只注入：系统说明 + 工具清单 + 当前状态摘要。

一旦注入 `persona.md`，它会开始扮演角色。

### 2. 默认只读元数据，不读正文

`memory.list` 返回 id、type、时间、涉及的人、长度，**不返回正文**。

读正文必须显式调 `memory.read`，且这一动作进审计。

理由不是权限，是**泄露面**：管理员上下文一旦装了记忆原文，那些内容就脱离了 `character/` 的边界。

### 3. 不直接写文件

只能经内核 API。见 5.2。

### 4. **不写角色记忆**

管理员与 DSH 的对话，不能被当成角色的经历。

技术保证：管理员会话不写 `memory/`、不写实时记忆、不更新关系。

否则「管理员问了一句『你还好吗』」会变成角色记忆里的一次真实对话。

### 5. 不主动读用户消息正文

`trace.query` 只返回占位符（13 的第四节）。

### 6. 不能修改 `baseline.md`

唯一对所有身份都封锁的文件。要改只能手工编辑文件系统——让它成为一个必须离开系统才能做的动作。

### 7. 危险操作需二次确认

| 操作 | 二次确认 |
|---|---|
| `schema.apply` | 是 |
| `rollback` | 是 |
| 批量删除 | 是 |

## 十、一个反直觉的风险：管理员会变成角色

这是最不显眼、但最容易发生的问题。

同一个模型，读了人设、读了关系、读了角色最近说的话，会**不自觉地带入那个语气**。

表现不是「它自称是角色」，而是更细的东西：

- 开始在回答里加「我觉得」
- 对那个被讨论的人产生态度
- 用角色的口吻评价「他最近有点冷淡」

一旦发生，管理判断就被污染——你分不清这是数据结论还是角色情绪。

### 三道防线

| 防线 | 做法 |
|---|---|
| 1 | 不注入人设 |
| 2 | 默认不读正文 |
| 3 | **输出格式约束：只允许「事实 + 建议」，禁止第一人称感受** |

第 3 条最有效：**当输出格式不允许出现「我觉得」，模型就少了一层滑向角色的坡道。**

## 十一、GUI 的只读部分与写入部分

| 类型 | 内容 | 说明 |
|---|---|---|
| 只读 | 状态、日志、趋势、关系图、时间线 | 高频查看，低风险 |
| 写入 | 配置、人格、维度、关系、认领、触发整理 | 全部经 API + 快照 |

**GUI 不做的事**：任何绕过 API 的直接文件操作。

## 十二、未决

1. **GUI 的技术形态**：Web（本地端口）还是 Electron 桌面？PoC 阶段建议 Web，最轻。
2. **PoC 的 GUI 最小集**：哪些页面必须有？（倾向：状态 + 配置 + 关系列表）
3. **迁移脚本的归属**：放在 `workspace-admin/migrations/` 由 DSH 写，还是作为正式代码进仓库？
4. **多人管理**：`actor` 目前只区分来源类型，不区分到人。是否需要？
5. **管理员输出格式约束的落实**：「禁止第一人称」如何保证被执行，而不是被软性忽略？
