## 一、PoC 要验证什么

架构已经闭环，现在要回答的不是「还能设计什么」，而是**「哪些假设必须先被证实」**。

整体设计依赖四个假设：

| # | 假设 | 能否在短周期验证 |
|---|---|---|
| A1 | 角色能跨会话记住人 | ✅ 几天可见 |
| A2 | 同一角色在不同场合表现不同 | ✅ 几天可见 |
| A3 | 角色会自己整理、自己成长 | ⚠️ 机制可验，效果需数月 |
| A4 | 关掉渠道后数据完整、可迁移 | ✅ 一次即可 |

### 一个关键区分

> **PoC 验证的是「机制通了」，不是「效果像不像人」。**

「像不像人」需要几个月的真实互动才能判断，PoC 周期内看不到。

所以 A3 在 PoC 里只验证**整理会按时发生、产物格式正确**，不验证「它真的变聪明了」。

## 二、最小范围

只做「不做就无法验证 A1 / A2 / A3-机制」的部分。

| 模块 | PoC 做 | PoC 不做 |
|---|---|---|
| **渠道** | **仅 QQ**（OneBot via SnowLuma），适配器为独立进程 | 微信、多渠道路由 |
| **群聊** | **至少一个群的完整链路**：群节点、κ、`member_of` | 多群调度、`per-group` 标识 |
| **内核** | 注意力队列（严格单会话） | 饥饿处理、社交偏好 |
| **DSH 接口** | `deliver` / `reply` 一次往返 | 完整四层 `idle` |
| **实时记忆** | 体验块 + 事实便签，单一文件 | TTL 精细策略、归档轮转 |
| **长期记忆** | 条目格式、按 `people/` + 月聚合 | 归档区、周记、月报 |
| **关系网络** | 节点（person + group）+ 边 + **`by_identity` 索引** | 认领界面 |
| **人格侧面** | schema + **4 个维度**（closeness / formality / trust / power）+ 阈值查表 | L2 维度演进、群专属维度 |
| **输出形式** | 延迟 + 分段（21 说性价比最高） | 「正在输入」状态、多气泡精细控制 |
| **整理** | **L0 + L1** | L2 / L3 |
| **管理入口** | 最小 GUI（状态 / 配置 / 关系列表）+ admin 工具 | 趋势图、关系图、时间线回放 |
| **安全** | L2 确定性拦截 + 静默审计 | L1 完整基线、L3 输出兜底 |

### 为什么 L1 必须在 PoC 里

如果只做 L0，上下文一满就无法继续——**PoC 跑不过第一周**。

L1 的「落盘 → 压缩 → 校验」是让系统能长期运行的最低条件，不是优化项。

### 为什么 `by_identity` 必须在

角色收到任何一条消息，第一件事是「这是谁发的」。没有这个索引，关系网络就是死的。

它是**热路径上唯一的强制依赖**。

### 为什么 PoC 必须包含一个群

因为验收标准第 2 条是「同一人、两个场合，表现可观察地不同」——**只做私聊就没有两个场合**。

而且群是 G1（群节点）、G12（κ）、15 的 8.9（trust 群上限）三者唯一的验证场景。不做群，这三块设计等于没验证过。

但只做**一个**群，不做多群调度——那属于 08 的「饥饿」问题，PoC 不碰。

## 三、明确不做（比「做什么」更重要）

下面这些**全部划掉**，哪怕它们已经在文档里设计完成：

| 不做 | 原因 |
|---|---|
| 多渠道 | 单渠道足以验证 A1 / A2 |
| 主动聊天 | 与核心假设无关 |
| 饥饿 / 社交偏好 | 单渠道 PoC 里几乎不会遇到 |
| 向量检索 | 几百条记忆用目录 + grep 就够 |
| 多角色 | 一个角色足够验证全部假设 |
| 复杂可视化（趋势图、关系图、时间线） | 最小 GUI 足够验证四个假设 |
| 认领 UI | 手改 index 更快 |
| L2 / L3 整理 | 需要数月数据才有意义 |
| 周记 / 月报 | 同上 |
| 维度演进 | 同上 |

> **这份清单的作用不是省事，是防止范围膨胀。**
> 每加一项，PoC 的完成时间就往后推一周。

## 四、四个阶段

每个阶段都能**独立跑通并观察**，不要一次做完再测。

### 阶段 A · 骨架（能说话）

```
渠道 → 内核（单会话队列）→ DSH → 回复 → 渠道
```

- 无记忆、无关系、无人设
- 目的：证明链路通，验证 DSH 接口能力

**这一阶段就要回答最大的技术风险**（见第六节）。

### 阶段 B · 记忆（能记住）

- 长期记忆条目格式 + 按主体月聚合
- 实时记忆（体验块 + 事实便签）
- 每轮注入：时钟 + 事实视图 + 在场视图

**验收**：隔三天再聊，角色能自然接上上次的话题。

### 阶段 C · 关系与侧面（认得人、看场合）

- 关系节点 + 边 + `by_identity` 索引
- schema + 三个维度（`closeness` / `formality` / `trust`）
- 阈值量化 + 滞回 + 行为集

**验收**：同一个人在群聊和私聊里，角色的表现可观察地不同。

### 阶段 D · 整理（会自己收拾）

- L0：归档实时记忆、扫 `promise`
- L1：落盘 → 压缩 → 校验
- 简版自述

**验收**：连续跑一周，记忆不丢、上下文不爆、有自述产出。

## 五、验收标准

| # | 标准 | 怎么测 |
|---|---|---|
| 1 | **记忆连续** | 隔三天再聊，角色能提起上次的事，且不是复述原句 |
| 2 | **侧面存在** | 同一人、两个场合，行为差异可观察（不是靠自我声明） |
| 3 | **整理按期发生** | 一周内 L0/L1 都跑过，且无数据损坏 |
| 4 | **可迁移** | 打包 `character/`，换机器恢复，行为一致 |

第 2 条最容易自欺：不要问角色「你对这两个群感觉一样吗」，要**看它说的话**。

## 六、最大的技术风险：DSH 接口能力（已实测，2026-10-23）

原判断：这是唯一可能在阶段 A 就卡死的地方。

**三项都测过了**，见 [28-探针方案](28-探针方案.md) 与 `probes/result.yaml`。

### 6.1 两条架构要求的实测结果

| 要求 | 结果 | 依据 |
|---|---|---|
| 一次同步往返（不轮询） | ✅ | `session/prompt` 同步返回，无轮询需要 |
| 只推增量（session 自己持有上下文） | ✅ | 同 session 多轮延续通过；且 `systemPromptUpdate: "in-history"` 证明上下文在 DSH 侧累积 |

**所以 [05](05-内核接口形状.md) 的接口形状不需要改。**

### 6.2 但第三个探针的答案变了

原设计问「能否主动触发压缩」，实测答案是：

> **不需要触发，也不该触发——压缩在 HTTP 代理层自动完成。**

由此三处修正（详见 [27](27-上下文压缩.md)）：

1. 内核**不实现**压缩，只配置代理阈值
2. 阈值支持绝对 token 数，且**可热改**（不用重启）
3. **窗口必须运行时读**——DSH 配置与代理实测不一致，且随 provider 变化；写死会在换 Key 后失效

### 6.3 一个新风险（原设计没预见到）

**人格是配置级，不是请求级**（见 [29-人格部署](29-人格部署.md)）。

后果：改人格 = 改配置 + 重启 + 重建会话。

这不在原风险清单里，但它改变阶段 A 的做法：

> **跑 PoC 之前就要把人格定下来。** 否则中途换代要重建所有会话。

### 6.4 结论

阶段 A **不再有技术不确定性**，可以开始写代码。

唯一保留的未验证项是 T7（压缩对单轮的影响），它只影响 [17](17-故障与降级.md) 的降级策略，不影响接口形状。

## 八、PoC 之后

| 方向 | 前置条件 |
|---|---|
| 多渠道 | A1 / A2 已证实 |
| L2 / L3 整理 | 跑满一个月，有足够数据 |
| 维度演进 | 出现「现有维度解释不了」的实际案例 |
| 向量检索 | 条目数上千，grep 开始失效 |
| 控制台编辑 | 手改配置成为真实痛点 |

## 九、未决

1. **渠道选型**：微信（WeChatAgent 链路完整但有 Hook 风险）还是 QQ（SnowLuma 更稳定但需外部网关）？
2. **PoC 周期**：四周够不够？阶段 D 的「连续一周」是硬要求。
3. **迁移测试的频率**：只在最后做一次，还是每阶段都做？
4. **探针失败后的退路**：如果 DSH 不支持增量，是改架构还是换推理后端？
