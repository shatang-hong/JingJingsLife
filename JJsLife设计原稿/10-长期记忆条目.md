## 一、先划边界：这里只存什么

「记忆」这个词太宽，容易和其他两层重叠。三者分工：

| 载体 | 存什么 | 特征 |
|---|---|---|
| `relations/` | 关系的**当前状态** | 会被覆盖，只留最新值 |
| `knowledge/` | 与具体人无关的**知识** | 可检索，可引用来源 |
| **`memory/`** | 发生过的**事**、关于人的**事实** | **只追加，不覆盖** |

一句话：

> **关系是「现在怎样」，记忆是「曾经怎样」，知识是「普遍怎样」。**

判断一条信息该进哪：如果它会因为新信息而**被修改**，进 relations；如果它只是**被补充**，进 memory。

---

## 二、物化与不可物化的分界

这是本设计最重要的一条。

一条记忆由两部分组成：

| 部分 | 性质 | 作用 |
|---|---|---|
| **frontmatter** | 可物化：时间、类型、人物、重要度 | 检索、衰减、审计 |
| **正文** | 不可物化：自然语言叙事 | 角色「理解」这件事 |

> **结构负责找到它，语言负责理解它。**

如果把正文也拆成字段，记忆就变成了数据库记录，角色会记得「事实」但不记得「经过」——那就是木偶。

所以正文必须是自由文本，且**不要求格式统一**。它可以写得像日记：

```
小明说他下个月要换工作，去杭州。
他有点犹豫，因为女朋友在上海。
说到这个的时候他停了很久才继续。
```

这段里有情绪、有停顿、有没说出口的东西——这些都不是字段能装的。

## 三、文件组织

### 3.1 活动区：按主体 + 月份

```
memory/
├── core/                          # 角色自我认知、重大事件
│   └── 2026-10.md
├── people/
│   └── n_zhangsan/
│       ├── 2026-09.md
│       └── 2026-10.md
├── groups/
│   └── n_qq_123456/
│       └── 2026-10.md
├── topics/
│   └── 装修/
│       └── 2026-10.md
├── journal/                       # 角色的自述（周记 / 月报）
│   ├── week/2026-W43.md
│   └── month/2026-10.md
├── archive/                       # 归档区：按时间
│   └── 2026-10/
│       ├── 2026-10-01.md
│       └── 2026-10-summary.md
└── _index.json                    # 派生索引（覆盖活动区 + 归档区）
```

**为什么活动区按主体、归档区按时间**：

| 区 | 组织方式 | 原因 |
|---|---|---|
| 活动区 | 按主体 + 月 | 整理时需要按人聚合 |
| 归档区 | 按时间（年-月 / 日） | 回溯时按时间翻，且不再频繁访问 |

**为什么聚合而不是一条一文件**：

| 方案 | 问题 |
|---|---|
| 一条一文件 | 一年几千个文件，目录爆炸 |
| **按主体 + 月份** | 文件数可控；同月的事放一起，整理时上下文连贯 |

归档的时机、命名与不可逆规则见 [11-整理会话](11-整理会话.md) 第七节。

### 3.2 一条记忆长什么样

月份文件内部，每条记忆是一个块：

````markdown
### m_20261023_001

```yaml
type: event
when: 2026-10-23T21:14:00+08:00
session: qq:group:123456
people: [n_zhangsan]
importance: 0.7
confidence: 0.9
source: dialogue
recall_count: 3
last_recalled: 2026-10-25
status: active
```

小明说他下个月要换工作，去杭州。他有点犹豫，因为女朋友在上海。
说到这个的时候他停了很久才继续。
````

文件头部再放一份文件级 frontmatter（主体、月份、条目数），供快速扫描。

## 四、五种类型

| type | 例 | 特殊之处 |
|---|---|---|
| `event` | 上周三和他吵了一架 | 有明确时间点 |
| `fact` | 小明喜欢猫，讨厌 Java | 长期有效，无时间点 |
| `preference` | 这个群喜欢玩梗，不爱长文 | **影响说话风格** |
| `promise` | 我答应帮他查资料 | **有截止条件，需要被提醒** |
| `emotion` | 那天他情绪很低 | 影响后续几轮的态度 |

### `promise` 是唯一需要主动检查的类型

其他四种都是「被读到才有用」，`promise` 是「不被读到就出事」。

它需要：

- 一个截止条件（时间点，或「下次他提到 X 时」）
- 在整理时被扫一遍
- 未完成且已过期的，升格为「欠着的事」

这正是「闲暇时整理」的一个具体用途——不只是压缩，还有**想起来该做什么**。

## 五、衰减：不做一个独立机制

**结论**：衰减没有单独的算法。它的自然体现是**上下文压缩**。

### 5.1 真正的衰减发生在「编码」，不在「存储」

这是与人类最接近、也最省事的一点：

> **遗忘首先是「没记住」，不是「记住了又丢掉」。**

人类记忆的遗忘，很大比例发生在编码阶段——注意力有限，没留意的根本没进记忆。所谓遗忘曲线，更多是提取失败，而不是存储被削弱。

对应到这里：**一次对话被压缩后，细节进不了长期记忆，就等于自然遗忘。**

- 压缩是时间驱动的（近的详细，远的模糊）
- 压缩由 DSH 做，重要性判断天然内含其中（模型会保留它认为重要的）
- 因此**不需要额外的权重、衰减曲线、调参**

### 5.2 否决原构想的「衰减曲线」

三条理由：

1. 自动衰减需要内核计算权重——那是推理，违反 I3
2. 衰减曲线是人为假设，真实遗忘没那么规整
3. 一旦自动降低就再也升不回来，除非有人还记得它曾经重要

### 5.3 唯一的代价（可选补偿）

压缩是**真删除**；人的遗忘是**提取失败**。差别只有一条：

> 人会「突然想起来」，被压缩掉的记忆不会。

若想保留这种可能，成本最低的做法是：**压缩时只留线索，不留内容**。

即留一条「曾经有过这件事」的索引（时间、人物、一句话标签）。它平时不出现，只在有人提起相关的事时才被翻出来。

成本接近零，且不引入任何新机制。若认为没必要，跳过也不影响其他设计。

### 5.4 两个客观信号（不做衰减，但保留判断依据）

| 信号 | 谁来维护 | 含义 |
|---|---|---|
| `importance` | DSH 写入时给 | 当时觉得多重要 |
| `recall_count` / `last_recalled` | 内核（纯计数） | 后来真的被用过几次 |

整理时，DSH 看这两个数决定：保留、合并、还是标记 `deprecated`。

**分两级**：

| 级别 | 能做什么 |
|---|---|
| 日常整理（L1） | 只做**合并** |
| 月度整理（L3） | 才做**标记 `deprecated`** |

理由：只有月度有足够长的视野判断「这件事后来再没被提起过」（11 的 6.2）。

> **判断是 DSH 的，内核只提供计数。**

内核做的是「+1」和「记时间」，不构成推理。

### 5.5 为什么不真删

`status: deprecated` 而不是删除文件。

- 保留「曾经这么想」的痕迹，符合 I4 的可回溯
- 万一以后需要，还能翻出来
- 删除不可逆，记忆系统不该有不可逆操作

## 六、单一真源 + 多路索引

一条记忆只会**存在一处**。它可能同时属于「某个人」「某个主题」「某个月」，但不复制。

查找靠索引，不靠目录冗余。

```
memory/_index.json
{
  "version": 1,
  "by_person":  { "n_zhangsan": ["m_...001", "m_...017"] },
  "by_type":    { "promise": ["m_...009"], "event": ["m_...001"] },
  "by_month":   { "2026-10": ["m_...001", "m_...009"] },
  "by_session": { "qq:group:123456": ["m_...001"] }
}
```

规则与 07 的关系索引一致：

| 规则 | 说明 |
|---|---|
| 索引派生，可重建 | 丢了从文件重扫 |
| 不一致时以文件为准 | 索引不是事实 |
| 由内核在写入时同步更新 | 纯字符串操作 |

## 七、append-only 的边界（重要修正）

之前说「长期记忆靠追加天然可回溯」，这话只对了一半。

两条规则要分开：

| 记忆层 | 写入模式 | 原因 |
|---|---|---|
| **实时记忆** | 严格 append-only | 高频、实时、怕丢、怕冲突 |
| **长期记忆** | 整文件重写 + 快照 | 低频、批量、需要整理与合并 |

长期记忆必须允许重写——否则 DSH 无法「把三件小事合并成一件大事」，而这正是整理的核心动作。

安全性由**单写者 + 写入前快照**保证，不靠 append-only。

## 八、读写权

| 动作 | 谁 |
|---|---|
| 建月份文件骨架 | 内核（纯规则） |
| 写条目、合并、标记 deprecated | DSH |
| 更新 `recall_count` | 内核（纯计数） |
| 强制删除某条 | 管理员 |
| 重建索引 | 内核 |

## 九、与「检索上限」的关系

这是 08 里标记的开放问题。

当前方案的上限：

| 规模 | 可行性 |
|---|---|
| 几百条 | 目录 + grep 完全够 |
| 几千条 | 需要靠索引先缩小范围 |
| 万条以上 | 必须引入向量检索 |

**现在不做向量库**，但留了位置：索引文件的结构已经按「多路缩小范围」设计，以后接向量只需要再加一路 `by_embedding`，真源不变。

## 十、未决

1. **`importance` 的主观性**：DSH 打分会不会越打越随意？是否需要校准机制？
2. **条目 id 的生成规则**：现在是 `m_日期_序号`，跨文件是否可能重复？
3. **`promise` 的截止条件怎么表达**：自然语言（「下周三之前」）需要解析，谁来解析？
4. **跨主体记忆**：一件事同时涉及三个人，归谁的文件？现在倾向于「首次提及者」，但可能不合理。
5. **`deprecated` 的清理**：永远不删的话，文件会越来越大，需要归档策略。
