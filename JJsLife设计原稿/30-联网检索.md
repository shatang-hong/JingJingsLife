# 30 · 联网检索

> 性质：横切能力。涉及工具权限、注入防护、隐私、记忆可信度。

## 一、结论先行

| 项 | 决定 |
|---|---|
| 档位 | **只有两档：`off`（默认）/ `on-demand`** |
| 默认 | **`off`** |
| 工具 | **不自研**，用 DSH 内置的 `@deepseek-ai/dsh-tool-web` |
| 落地方式 | 预设里挂不挂 `tool-web` |
| 注入防护 | **官方已内置**（结果标记为「外部不可信数据」），我们只补一条内核规则 |
| 我们真正要做的 | **隐私闸门**、**用量节制**、**记忆归属** |

## 二、为什么它特殊

联网有一个别的问题没有的性质：

> **它是唯一能把「不可信内容」送进上下文的路径。**

其它入站内容都有边界：

| 来源 | 可信度 | 为什么 |
|---|---|---|
| 群消息 | 有边界 | 来自渠道，是「人说的话」 |
| 记忆文件 | 高 | 角色自己写的 |
| 知识库 | 中 | 有来源与置信度（[18](18-知识库.md)） |
| **网页内容** | **无边界** | **任何人都能写，且专门写给模型看** |

于是出现一个 `03` 那三层拦截**没有覆盖**的情况：

> **L1 基线（prompt 里的硬约束）可能被网页内容绕过。**

`03` 防的是「角色**说错话**」，联网要防的是「角色**被骗**」。**防线不一样。**

## 三、两档

| 档 | 行为 | 什么时候用 |
|---|---|---|
| **`off`**（默认） | 预设里不挂 `tool-web` | 出厂状态 |
| `on-demand` | 挂上，DSH 判断需要才搜 | 管理员显式开启 |

### 3.1 为什么默认 off，但 on-demand 必须存在

默认 off 是安全上的保守：**出厂状态下角色没有任何对外访问能力**。

但 `on-demand` 不能省，理由不是「备着总没错」，而是：

> **知识库的积累依赖信息流入。** 一个从不联网的角色，只能从对话里学——
> 而对话里出现的东西，大多是它已经知道的。

知识库要「根据判断来积累」，就必须有一个能**主动获取新信息**的通道。否则它只能沉淀闲谈，沉淀不出知识。

所以两档的关系不是「安全 vs 功能」，而是：

| 档 | 角色形态 |
|---|---|
| `off` | 只从对话里认识世界 |
| `on-demand` | 会去查、会学，但只在觉得需要时 |

**前者是出厂，后者是养成。** 由管理员决定角色处在哪个阶段。

### 3.2 没有第三档

原设计里有个 `proactive`（主动搜）。**去掉。**

主动检索意味着角色会「突然去查东西」——那是助手的行为，不是人的。人不会在聊天中途突然查资料然后宣布结论。

## 四、落地：用内置工具，不自研

`@deepseek-ai/dsh-tool-web` 提供两个工具：

| 工具 | 作用 |
|---|---|
| `web_search` | 搜索，返回答案与来源 URL |
| `web_fetch` | 抓页面正文 |

它在 `ptc` / `standard` / `cordis` 预设里**已经挂好了**：

```yaml
- id: tool-web
  name: '@deepseek-ai/dsh-tool-web'
  config:
    fetch: true
    searchTimeoutMs: 60000
```

`minimal` 预设里没有——**这就是天然的 `off`**。

### 4.1 两档怎么切

| 档 | 做法 |
|---|---|
| `off` | 用一个不含 `tool-web` 的预设（如 `minimal`），或给它加 `disabled: true` |
| `on-demand` | 用含 `tool-web` 的预设 |

也可以在同预设里只开一个：`{ search: false }` 或 `{ fetch: false }`。

**不需要写一行代码。**

### 4.2 一个前提：后端要就绪

工具依赖两个后端：

```
@deepseek-ai/dsh-web          （web 能力缝）
@deepseek-ai/dsh-web-search-exa（Exa 搜索后端）
```

**后端缺失时，工具仍然可见，但调用会返回结构化错误。**

所以部署时必须确认：

> 后端没配好 = 实际是 `off`，但模型会「以为能搜」而反复尝试。

这比干脆不给工具更糟——**因此 `off` 应该真的不挂工具，而不是挂了让它失败**。

## 五、三条约束：官方做了一条半

### 5.1 注入防护：官方已做，我们补一条

`dsh-tool-web` 的原文：

> 结果会把提供方控制的文本标记为**外部不可信数据**，而抓取到的 HTML 会排除活动与隐藏内容。

也就是说，「把网页内容标成不可信」这件事**不用我们做**。

但插件管不到内核侧的行为，所以还要补一条：

| 规则 | 谁执行 |
|---|---|
| 网页内容不得写进 `identity/` 与 `baseline.md` | **内核**（写入层拦截） |
| 网页内容默认不入 `memory/core/` | 内核 |
| 引用时必须标 `source: web` | DSH（[07](07-关系网络.md) 的枚举） |

**第一条是硬的**：插件把内容标成「不可信」，但只有内核能阻止它被写成「角色的自我认知」。

### 5.2 隐私闸门：内核拦查询词

**不能让 DSH 把聊天原文直接当查询词发出去。**

真实场景：群里有人说「我身份证后四位是 1234」，角色为了查天气把整句话搜出去。

查询词发出前必须过内核的**形态检查**（与 `03` 的 L2 同一套）：

| 拦什么 | 例子 |
|---|---|
| 凭据 / 密钥 | `sk-…`、`Bearer …` |
| 身份标识 | 身份证、手机号、邮箱 |
| 本机路径 | `/home/xxx/…` |
| 与近期消息高度重合的长串 | 间接泄露原文 |

**只拦形态，不判语义**——内核不做推理（I3）。

拦截时**静默丢弃查询**，不告知 DSH。

> **这是官方没做、且必须由内核做的一条。** 因为只有内核知道「这条消息是谁发的、属于哪个会话」。

### 5.3 用量节制：每段最多 3 次

| 约束 | 值 | 理由 |
|---|---|---|
| 每 segment 最多 | 3 次 | 超过就是在查资料，不是在聊天 |
| 同一 URL 不重复抓 | — | 白费 |
| 单次结果上限 | 约 2k token | 防单页撑爆上下文 |
| 失败重试 | ≤ 1 次 | 避免卡住这一轮 |

**这条是兜底**：即使 5.1 的防护被绕过，次数上限也能把损害限制在「三段对话内」，而不是「整个会话被污染」。

## 六、搜索结果算谁的记忆

搜到的内容如果直接进 `memory/`，就变成「角色记得的事」，而它其实只是「网上看来的」。

| 来源 | `source` 值 | 能不能当事实说 |
|---|---|---|
| 他说的 | `stated` | ✅ |
| 角色观察到的 | `observed` | ✅ 措辞谨慎 |
| 知识库沉淀的 | `knowledge` | ✅ 标来源 |
| **网上搜到的** | **`web`** | ⚠️ **必须说「我查到…」，不能说「就是…」** |
| 角色推测的 | `inferred` | ❌ |

`web` 已作为 [07](07-关系网络.md) 的 `source` 枚举新增。

**默认情况下网页内容不入长期记忆**——它属于「当下用到的东西」，用完就丢。只有经过 [18](18-知识库.md) 的入库闸门（人工或高置信度），才沉淀。

这条很关键：

> **联网 ≠ 学会。** 搜到的进知识库要过闸门，否则角色会变得「什么都知道但什么都不深」。

## 七、与 PoC 的关系

**PoC 用 `off`。**

理由：`12` 的四个假设（A1–A4）没有一个需要它，而它会引入最大的外部不确定性（网络、后端、可信度、注入）。

| 阶段 | 档位 | 说明 |
|---|---|---|
| PoC | `off` | 用不含 `tool-web` 的预设 |
| V1 | `on-demand` | 补 5.2 / 5.3 |
| V2 | 接 `18` 的知识沉淀闸门 | |

**契约现在留**：`source: web` 已写进 07，实现空着。

## 八、可复用的现成件

| 来源 | 复用什么 |
|---|---|
| **DSH 内置** | `dsh-tool-web`（工具 + 外部不可信标记），优先用它 |
| qq-bridge | `safe-fetch.js` —— **SSRF 防护**：禁内网地址、限协议、限重定向 |
| WeChatAgent | `web_search` / `web_reader` 的工具形状（作为对照） |

**SSRF 这条要单独确认**：`dsh-tool-web` 的 README 讲了「排除隐藏内容」，但**没提内网地址拦截**。

角色在工作区里跑，能访问内网就意味着一句「帮我看看 127.0.0.1:8080」就能探测本机服务。

> 这是待实测项：`dsh-web` 抓取时是否拦截 `127.0.0.1` / `10.x` / `169.254.x`。

---

## 九、未决

1. **SSRF 防护是否内置**：见第八节，需实测 `dsh-web` 的抓取行为。
2. **搜索后端的选择**：Exa 是默认，能否换？换后端会不会带新的信任问题？
3. **结果的缓存**：同一话题反复搜，要不要复用？缓存会变成「不可信内容长期驻留」吗？
4. **注入防护的实际强度**：官方标了「不可信」，但模型是否真的把它当数据而非指令——没有可靠测法，只能红队式尝试。
5. **`off` 到 `on-demand` 的切换时机**：管理员什么时候该开？开了之后知识库的增长曲线会变，这算不算「角色的人生阶段」？
