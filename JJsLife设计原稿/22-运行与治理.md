# 22 · 运行与治理

> 上游：全部

## 一、成本与预算（G6）

> **默认关闭。** 预算系统保留设计但不默认启用；需要限额时才参照本节。

三份预算必须**分开记账、分开限额**：对话预算（每轮注入 + 输出 + 延迟，高频可预测）、整理预算（L0–L3 整理，低频、波动极大，L3 可能一次吃掉一天额度）、检索预算（知识检索与联网，按需不可预测）。混在一起会出事故：一次月度整理吃掉全部额度，后面几天角色「失语」。

注入开销分两类：**固定**（人格 + 身份内核 + 安全基线，必须小且有硬上限；时钟 + 关系投影，极小）；**可变**（事实视图 N 条便签，按相关性截断；知识片段，只在 DSH 主动检索时产生）。

> **固定开销不能随角色成长而膨胀。** 这是架构红线，不是优化项。

超预算不能硬截断（会失去连续性），按序降级：①缩事实视图条数 ②减知识检索 ③缩输出长度 ④**绝不削减人格与身份**。

> **为了省钱牺牲「它是谁」，等于用最贵的方式毁掉这个项目。**

预算紧张不必表现为性能下降，可表现为**行为**：充足时话多愿展开，紧张时回复变短、少接话、偶尔「嗯」——与 21 的长度参数天然兼容，**人累了也会变短，这是作息不是缺陷。**

记账沿用 qq-bridge 的 `token-ledger`：每轮一条，按节点 / 级别 / 天聚合，同时是 GUI 看板数据（14）与预算依据。

## 二、多角色（G8）

`character/` 是一个完整角色的全部；多角色 = 多个目录，不改任何数据结构。

**硬约束：一个角色一个内核实例。** 理由是语义：注意力属于角色，是主体属性而非资源分配（I2）；共享内核就会问「哪个角色优先」，这问题本身说明设计错了。

不共享的：记忆、关系、人格（❌ 完全不共享）、知识库（❌ 各自一份，即使内容相同）、渠道账号（❌ 一个账号只能被一个角色占用）。可共享的：推理后端（DSH，同实例不同 session）、管理入口（GUI，同界面多角色面板）。「一个账号被两个角色占用」必须禁止，否则同一批人会被两个身份轮流接待——那是事故不是功能。

**压缩代理同样不能共享**：`billion-context` 的阈值是**全局配置**而非 per-session，共用会互相干扰且无法分辨请求归属，因此**每个角色必须有独立代理实例**（不同端口）。这与「一个角色一个内核实例」是同一原则的两面：**凡是持有角色级配置的组件，都不能跨角色共享。**

## 三、退役（G9）

| 方式 | 渠道 | 进程 | 数据 | 它还「在」吗 |
|---|---|---|---|---|
| **停用** | 断开 | 运行 | 保留 | **在，还在变化**（整理照常） |
| **封存** | 断开 | 停止 | 打包 | 不在，但可复活 |
| **销毁** | 断开 | 停止 | 删除 | 真的没了 |

区别不是程度而是**性质**：停用是它还在生活，封存是它睡着了，销毁是它死了。**停用**最容易被忽略也最该被支持——它是唯一符合「数字生命」直觉的状态，必须是正式的一等状态，不是「配置里把渠道删掉」。

销毁必须有冷静期（记忆不该有不可逆操作，见 10 的 5.5；但删除是用户权利，见 G10）：发起时二次确认并输入角色名；**2 天**冷静期内数据移入 `_trash/`，不可运行、可恢复；到期真正删除，并留一条只有创建时间、销毁时间、名字的极简记录，**不留内容**。

## 四、隐私与数据权利（G10）

三个主体：管理员（所有者，拥有角色数据）、对话者（群友 / 好友，**被记录且通常不知情**）、平台 / 模型提供商（处理数据）；对话者这一层是整个项目最大的伦理风险点。

架构能做三件事：**可删除**（管理员能删且删得干净，含索引、快照、归档、引用它的自述）；**可导出**（角色数据完整带走，见 06 的导出契约）；**不欺骗**（被直接问「你是 AI 吗」时不否认）。第三条最重要，应写进 `baseline.md`：

> **角色不主动宣称自己是人。**

**删除必须可验证**——不能只是 UI 上不见了。要删 `memory/` 条目、`relations/` 节点、`media/`；易漏索引文件、快照、归档区、自述里提到该人的段落、trace 日志里的 hash 关联。

> **删除不是删一处，是删所有引用。**

架构阶段只定原则：**提供「按节点全量清除」能力，并给出可核验报告**（清了多少条、涉及哪些文件）。不做两事：向群友广播「我被记录」、对话者自助删除（技术上无法验证身份）；它们留给产品和法律层面。

## 五、并发保护（G11）

多个内核实例同时操作同一个 `character/` 会破坏 03 的单写者不变式：开两个 GUI、崩溃后旧进程没死透、迁移时新旧机器同跑，都会双写或数据分叉。

用租约不用文件锁：文件锁崩溃时可能不释放、难判断持有者是否还活着；**租约（lease）**带过期时间，天然处理假死。机制：启动写租约（pid、启动时间、过期时间）→ 定期续约 → 拿不到则只读或退出（配置决定）→ 旧进程崩溃后过期，新进程接管。

只有**内核实例**需要租约（唯一写者）；管理员 DSH 与 GUI 不需要，它们只经 API 写（14 的 5.2）。所以只有单一持有者，不需要分布式协调。直接退出很难排查，更好的是**只读模式启动，GUI 显示「另一个实例正在运行」**。

## 六、五项的相互关系

租约（G11）决定谁能写 → 预算（G6）决定写多少、想多久 → 生命周期（G9）决定写不写、还写多久 → 多角色（G8）决定写到哪个目录 → 隐私（G10）决定写的能不能被彻底抹掉：**谁在写、写多少、写到什么时候、写在哪、能不能擦掉。**

## 七、未决（留给构建阶段标定）

1. **预算的具体数值**（仅在启用时）：每轮注入上限、每天对话额度、整理额度占比——必须用真实数据标。
2. **降级阈值的触发方式**（仅在启用时）：按 token 数还是按金额？峰谷价要不要参与？
3. **删除的可验证程度**：要不要提供「删除报告」的文件清单？
4. **租约的续约间隔**：太短会造成无谓写入，太长会导致接管延迟。
